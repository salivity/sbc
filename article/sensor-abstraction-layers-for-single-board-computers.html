Sensor Abstraction Layers for Single Board Computers

Developing embedded applications across diverse single board computer (SBC) models often presents integration bottlenecks due to differing pinouts, system-on-chip (SoC) architectures, and bus interfaces. This article explores the primary software architectures—including Hardware Abstraction Layers (HALs), kernel-level subsystems, containerized driver frameworks, and robotics middleware—that decouple high-level application logic from low-level hardware dependencies to ensure cross-platform sensor portability.

The Challenge of Multi-SBC Sensor Integration

Single board computers like Raspberry Pi, BeagleBone, NVIDIA Jetson, and Orange Pi utilize different SoCs, register maps, and Linux distributions. Directly binding application code to specific pin mappings or proprietary peripheral libraries creates tight coupling, forcing complete code rewrites whenever the host hardware changes. A standardized sensor abstraction layer solves this by establishing a uniform programming interface regardless of the physical bus (I2C, SPI, UART, or GPIO) or board layout.

Layered Hardware Abstraction Layer (HAL) Architecture

The classic HAL architecture separates software into distinct horizontal tiers:

  1. Application Layer: Handles domain-specific business logic, data processing, and telemetry without knowledge of underlying pin layouts.
  2. Abstract Sensor API: Exposes unified sensor interfaces (e.g., read_temperature(), get_acceleration()) using standardized data types.
  3. Platform Bus Driver Layer: Translates abstract bus commands into platform-specific implementations (e.g., standard Linux /dev/i2c-* calls or SoC-specific memory-mapped registers).
  4. Hardware Layer: The physical sensor and SBC hardware.

By isolating bus implementations behind polymorphic interfaces or abstract base classes, adding support for a new SBC requires only implementing the low-level bus wrapper rather than refactoring sensor drivers.

Linux Industrial I/O (IIO) Subsystem

For Linux-based SBCs, the kernel-level Industrial I/O (IIO) subsystem serves as a native, hardware-agnostic architecture for sensors such as ADCs, DACs, gyroscopes, accelerometers, and environmental sensors.

  • Unified Sysfs Interface: Exposes sensor data through standardized filesystem nodes under /sys/bus/iio/devices/.
  • Standardized Units: Automatically scales raw hardware outputs to SI units (e.g., millivolts, meters per second squared, pascals).
  • Device Tree Integration: Utilizes Device Tree Overlays (DTOs) to map sensors to specific I2C or SPI buses at boot time, removing the need for user-space board detection logic.

Applications read data via libiio or direct file operations, ensuring the user-space code remains completely identical across different SBC hardware platforms.

Modern User-Space Driver Frameworks

When kernel-level driver development is impractical, standardized user-space libraries decouple applications from specific hardware:

  • libgpiod: The standard Linux character device interface for GPIO access, replacing obsolete sysfs interactions and proprietary SBC GPIO libraries.
  • Unified Hardware Access Libraries: Frameworks like Adafruit CircuitPython/Blinka, MRAA, or Embedded HALs (in Rust) create an abstraction shim. They map vendor-specific pin definitions dynamically using runtime environment detection.

Middleware and Message-Driven Architectures

Complex systems deploy publish-subscribe middleware to completely isolate sensor drivers from data consumers:

  • Robot Operating System (ROS 2): Sensor drivers execute as independent nodes that read hardware and publish standardized messages (such as sensor_msgs/Imu or sensor_msgs/Temperature) over a DDS network. The processing software subscribes to the message topic without any reference to the SBC hosting the sensor.
  • Microservices and Containerized Drivers: Packaging hardware drivers into individual Docker or OCI containers that read from mapped device nodes (like /dev/i2c-1) and stream data via gRPC, REST, or MQTT. This isolates platform dependencies, simplifies dependency management, and exposes a uniform networking API across SBC fleets.

Dynamic Configuration and Runtime Pin-Mapping

To maximize portability, modern architectures implement declarative configuration models:

  • JSON/YAML Pin Mapping Schemes: Sensor pin numbers and bus addresses are stored in external configuration files, loaded dynamically at runtime based on the detected SBC model.
  • Factory Pattern Implementation: A centralized sensor factory reads the configuration, identifies the underlying board platform via /proc/cpuinfo or Device Tree models, instantiates the corresponding bus driver, and returns a generic sensor handle to the application.

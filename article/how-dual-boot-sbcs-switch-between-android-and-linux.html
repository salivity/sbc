How Dual Boot SBCs Switch Between Android and Linux

Dual-boot single board computers (SBCs) alternate between Android and Linux through a coordinated interaction of partitioned storage, bootloader configurations, and boot-selection triggers. By isolating each operating system's filesystems and kernel images on distinct drive sectors, the SBC relies on a low-level bootloader—most commonly U-Boot—to determine which environment to initialize at startup. This switching process happens via interactive menus, physical hardware toggles, or software flags written directly to the boot environment storage.

Storage Partitioning

To host both Android and Linux, the storage medium (such as an eMMC module, NVMe SSD, or microSD card) is divided into separate partitions. Android requires a specific layout consisting of partitions like boot, system, vendor, data, and recovery. Linux requires standard root filesystems (typically ext4 or btrfs) along with a dedicated /boot directory. While both systems may share a common raw boot sector where the initial boot code resides, their operating environments remain completely isolated on the drive.

The Role of U-Boot

The primary mechanism controlling the dual-boot process is Universal Boot Loader (U-Boot). When the SBC powers on, the system-on-a-chip (SoC) executes its internal Read-Only Memory (ROM) code, which locates and loads U-Boot. U-Boot reads specific configuration scripts (such as boot.scr, extlinux.conf, or built-in environment variables) to find the kernel image, the initramfs, and the Device Tree Blob (DTB) for the target OS. Depending on the configuration, U-Boot directs the hardware to boot either the Android kernel or the standard Linux kernel.

Boot Selection Methods

Alternating between the two environments is managed through several primary methods:

  • Interactive On-Screen Menus: The bootloader outputs a display menu over HDMI or serial console during a short countdown window. The user selects either Android or Linux using a connected keyboard, remote, or serial interface.
  • Software-Driven Flags: Users can switch systems from within a running OS. In Linux or Android, utility tools (such as fw_setenv) write a target value to the U-Boot environment partition. When the SBC reboots, U-Boot reads this flag, executes the corresponding boot sequence, and resets or preserves the flag based on the configuration.
  • Hardware Jumpers and GPIOs: Some SBC platforms use physical switches, jumper pins, or dedicated hardware buttons tied to general-purpose input/output (GPIO) lines. During initialization, U-Boot samples the electrical state of these pins; high voltage boots one OS, while ground boots the other.

Kernel and Device Tree Initialization

Once the selection is determined, U-Boot loads the appropriate Device Tree Blob (DTB) tailored to the target operating system. While Android and Linux on an SBC may share the same underlying processor, Android often requires specific Android Open Source Project (AOSP) kernel patches and unique memory allocations compared to a standard mainline Linux distribution. After U-Boot hands over hardware control to the chosen kernel and points it to the correct root filesystem, the operating environment finishes initializing its native user space.

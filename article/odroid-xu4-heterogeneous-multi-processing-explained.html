Odroid-XU4 Heterogeneous Multi-Processing Explained

The Odroid-XU4 single-board computer implements Heterogeneous Multi-Processing (HMP) through its Samsung Exynos 5422 system-on-chip (SoC), which utilizes ARM's big.LITTLE architecture. This article explains how the Odroid-XU4 coordinates its four high-performance ARM Cortex-A15 cores and four energy-efficient ARM Cortex-A7 cores simultaneously, examining the role of the Linux kernel scheduler, hardware cache coherency, and dynamic load balancing.

The Exynos 5422 Hardware Foundation

At the center of the Odroid-XU4 is the Samsung Exynos 5422 SoC. This processor features an octa-core setup split into two distinct clusters:

  • "big" Cluster: Four ARM Cortex-A15 cores clocked up to 2.0 GHz, designed for computationally heavy and latency-sensitive tasks.
  • "LITTLE" Cluster: Four ARM Cortex-A7 cores clocked up to 1.4 GHz, optimized for power efficiency and lower-intensity background tasks.

To enable these two different core microarchitectures to work together, the SoC integrates ARM's CoreLink CCI-400 (Cache Coherent Interconnect). The CCI-400 ensures hardware-managed cache coherency between the L2 caches of the Cortex-A15 and Cortex-A7 clusters, allowing threads to seamlessly move between cores without corrupting memory or suffering severe cache invalidation penalties.

Transition from Cluster Switching to True HMP

Early implementations of big.LITTLE relied on Cluster Switching or In-Kernel Switching (IKS):

  • Cluster Switching: Powered only one cluster at a time (either all A15s or all A7s).
  • In-Kernel Switching: Paired each A15 core with an A7 core, exposing only four virtual cores to the operating system at any given moment.

The Odroid-XU4 bypasses these limitations by employing true Heterogeneous Multi-Processing (HMP), also referred to as Global Task Scheduling (GTS). Under HMP, the operating system sees all eight physical cores at the same time. Any core can be active independently, allowing the system to run configurations such as two A15s and three A7s concurrently, or all eight cores simultaneously under peak load.

Kernel-Level Global Task Scheduling (GTS)

The core mechanism behind HMP on the Odroid-XU4 is the Linux kernel's HMP-aware task scheduler. The scheduler continuously monitors the computational demand of every individual software thread using load-tracking metrics.

  1. Load Tracking: The scheduler monitors the execution history of each running task to determine its average CPU utilization.
  2. Up-Migration Threshold: If a thread running on a Cortex-A7 core exceeds a predetermined workload threshold (e.g., heavy multimedia processing or compilation), the scheduler triggers an "up-migration," moving the thread to an available Cortex-A15 core.
  3. Down-Migration Threshold: When a thread's computational demand falls below a minimum threshold, the scheduler performs a "down-migration," moving the task back to a Cortex-A7 core to save energy and free up the Cortex-A15 for more demanding processes.
  4. Direct Placement: New or waking tasks are evaluated instantly; high-priority or historically heavy tasks are assigned directly to the big cluster, while small, short-lived tasks go to the LITTLE cluster.

Dynamic Voltage and Frequency Scaling (DVFS)

To complement HMP scheduling, the Odroid-XU4 uses independent Dynamic Voltage and Frequency Scaling (DVFS) planes for each core cluster. This enables the operating system to modulate the frequency and voltage of the Cortex-A15 cluster independently of the Cortex-A7 cluster.

When the system is idle or handling light tasks like basic networking, the A15 cluster can enter low-power sleep states (C-states) while the A7 cluster runs at reduced clock speeds. When a burst of processing power is required, the A15 cluster scales up frequency and voltage dynamically to deliver immediate compute performance.

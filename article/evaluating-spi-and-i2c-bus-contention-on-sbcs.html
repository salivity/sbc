Evaluating SPI and I2C Bus Contention on SBCs

This article provides an engineering guide on identifying, measuring, and resolving bus contention when Serial Peripheral Interface (SPI) and Inter-Integrated Circuit (I2C) protocols share physical routing or multiplexed pins on a single board computer (SBC). It outlines the core electrical conflicts between push-pull and open-drain architectures, protocol analysis techniques using oscilloscopes and logic analyzers, software-level pin multiplexing verification, and best practices for implementing hardware and firmware arbitration.

1. Understanding the Electrical Mismatch

SPI and I2C rely on fundamentally different electrical drive topologies. Evaluating contention begins with recognizing how these topologies interact on shared lines:

  • Drive Types: I2C uses open-drain (or open-collector) drivers with passive pull-up resistors, allowing multiple devices to pull the line low safely. SPI typically uses active push-pull drivers that actively drive lines both high and low.
  • Short Circuits: If an SPI master or peripheral actively drives a line high while an I2C device pulls it low, a direct path to ground is created. This causes excess current draw, degraded logic levels, and potential permanent damage to the SoC or peripherals.
  • Pull-Up Resistor Impact: The pull-up resistors required for I2C (typically 1kΩ to 10kΩ) can degrade high-speed SPI signals by altering line impedance, increasing capacitance, and rounding off high-frequency SPI clock edges.

2. Signal Integrity and Electrical Validation

Engineers use mixed-signal oscilloscopes (MSOs) to measure physical layer behavior during concurrent or alternating operations:

  • Voltage Level Verification: Measure \(V_{OL}\) (low-level output voltage) and \(V_{OH}\) (high-level output voltage). Contention appears as intermediate voltage levels (e.g., floating between 0.8V and 2.0V on a 3.3V bus) instead of clean logic transitions.
  • Current Measurement: Place a low-value current shunt resistor on the power rails of the bus transceivers or use current probes to detect unexpected current spikes during bus transactions.
  • Rise and Fall Times: Verify that bus capacitance does not violate the maximum rise time requirements for I2C (typically 300 ns for Fast Mode) or round the clock edges required for high-speed SPI transactions (often exceeding 10 MHz).

3. Logic and Protocol Collision Analysis

Digital logic analyzers decode protocol traffic to identify timing overlap and software misconfigurations:

  • State Tracking: Monitor the SPI Chip Select (\(\overline{\text{CS}}\)) line alongside I2C Start/Stop conditions to ensure that transactions are strictly mutually exclusive when pins are multiplexed.
  • NACK and Framing Error Detection: Contention on an I2C line usually manifests as unexpected NACKs (No Acknowledge) or missing clock pulses (SCL stretching failures). On SPI lines, contention manifests as corrupted MISO/MOSI bits or missing frame bytes.
  • Hold and Setup Time Violations: Confirm that switching between protocols provides sufficient guard time for line voltages to settle before the next protocol transaction begins.

4. Software Pin Multiplexing and Driver Arbitration

On modern SBCs running Linux or real-time operating systems (RTOS), contention often stems from race conditions in software:

  • Kernel Pin Control (pinctrl): Inspect the SBC’s Device Tree and pinctrl subsystem. Ensure pins shared via SoC multiplexers dynamically reconfigure their electrical characteristics (e.g., switching from open-drain to push-pull) before the peripheral driver initiates a transfer.
  • Mutexes and Locking: Evaluate device drivers to ensure a shared hardware lock (such as a kernel mutex or semaphore) serializes bus access. Neither driver should execute transactions until the previous transaction finishes and the pin multiplexer updates state.
  • Driver Hand-off Delays: Ensure the driver introduces a settling delay after reassigning a pin from SPI to I2C to allow the external pull-up resistor to pull the line completely high before an I2C Start condition is generated.

5. Architectural Mitigation Strategies

If hardware multiplexing or software arbitration fails to resolve contention, engineers deploy specific mitigation designs:

  • Hardware Bus Switches: Place a bidirectional analog switch (e.g., 74CB3Q series) or digital multiplexer controlled by a dedicated GPIO to isolate I2C and SPI signal paths physically.
  • I2C-to-SPI / SPI-to-I2C Bridges: Offload one protocol to an external bridge chip connected via a dedicated bus interface (e.g., using a dedicated USB-to-I2C bridge or UART bridge).
  • Software Bit-Banging: If hardware controller sharing is unavoidable and causes bus locks, move the slower I2C bus to dedicated spare GPIOs using a software bit-banging implementation, leaving the hardware controller exclusively for high-speed SPI.

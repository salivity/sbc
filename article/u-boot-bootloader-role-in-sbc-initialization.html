U-Boot Bootloader Role in SBC Initialization

Das U-Boot (Universal Boot Loader) acts as the critical intermediary between raw hardware and the operating system during the startup sequence of a single board computer (SBC). Upon power-on, an SBC lacks the operational context required to run a full operating system like Linux; U-Boot bridges this gap by initializing essential hardware components, managing boot configurations, loading the operating system kernel into memory, and transferring execution control to that kernel.

1. Secondary Program Loading (SPL)

Modern SBC System-on-Chips (SoCs) start execution from an internal, immutable Read-Only Memory (ROM) known as the Primary Bootloader. Because on-chip SRAM is extremely limited, the ROM code cannot load the entire U-Boot image directly into memory. Instead, it loads a stripped-down version of U-Boot called the Secondary Program Loader (SPL).

The SPL performs the bare minimum hardware initialization necessary to enable main system memory:

  • Initializes the system clock tree and power management integrated circuits (PMIC).
  • Configures and calibrates the external DDR SDRAM controller.
  • Identifies the boot media (such as an SD card, eMMC, or SPI flash).
  • Loads the full U-Boot binary into the newly initialized DDR RAM and executes it.

2. Full Hardware Subsystem Initialization

Once loaded into main RAM, the full U-Boot binary initializes a broader set of peripherals needed for boot operations. This phase establishes:

  • Storage Interfaces: Enables drivers for SD/eMMC, USB mass storage, SATA, or NVMe.
  • Communication Buses: Sets up I2C, SPI, and GPIO buses.
  • User Interactivity: Configures the serial UART console and display outputs (HDMI or LCD) to display boot logs and accept interactive user commands via the U-Boot shell.
  • Network Stack: Initializes Ethernet and PHY controllers to allow remote booting via protocols like TFTP, DHCP, or NFS.

3. Environment Variable and Script Processing

U-Boot relies on an internal environment storage block containing configurable key-value pairs. The most critical variables include:

  • bootcmd: The default command sequence executed after a countdown timer expires.
  • bootargs: The command-line parameters passed directly to the operating system kernel (e.g., root filesystem location, console baud rate, memory limits).

U-Boot checks whether user input interrupts the boot countdown. If unprompted, it executes bootcmd, dynamically scanning designated storage partitions or network endpoints for kernel images and boot scripts.

4. Device Tree and Kernel Preparation

Modern embedded Linux architectures decouple hardware topology from the kernel using Device Tree Blobs (DTBs). U-Boot reads both the compiled Linux kernel image (such as zImage or Image) and the corresponding .dtb file from the boot storage into specific addresses in RAM.

Before executing the kernel, U-Boot can dynamically modify the Device Tree in memory. It applies Device Tree overlays (DTOs), injects MAC addresses, passes memory bank allocations, and updates hardware status nodes based on runtime hardware detection.

5. Execution Handoff

In the final step, U-Boot disables interrupts, flushes processor caches, places the memory address of the Device Tree into a predefined CPU register, and executes a jump instruction (such as bootm or booti) directly to the entry point of the OS kernel. At this moment, U-Boot terminates its own execution, leaving the operating system in full control of the single board computer.

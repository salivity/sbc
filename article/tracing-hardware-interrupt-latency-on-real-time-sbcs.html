Tracing Hardware Interrupt Latency on Real-Time SBCs

Tracing hardware interrupt (IRQ) latency on a real-time patched (PREEMPT_RT) single-board computer (SBC) requires isolating the delay between a physical hardware signal and the execution of its corresponding interrupt service routine (ISR). This guide covers the essential techniques developers use to measure, trace, and minimize this latency. By combining hardware measurement tools like oscilloscopes with Linux kernel profiling utilities such as ftrace, trace-cmd, and cyclictest, engineers can pinpoint whether delays originate from hardware lines, kernel locking, power management, or thread scheduling.

1. Establish Ground Truth with Hardware Instrumentation

The most accurate method to measure pure hardware interrupt latency avoids software overhead entirely by using an external oscilloscope or logic analyzer.

  • Trigger Signal: Connect one probe to the external hardware line generating the interrupt trigger (e.g., a rising edge on a sensor line or GPIO pin).
  • ISR Acknowledgment: Configure the target ISR in your kernel module or user-space driver (via UIO/VFIO) to immediately toggle an unused, high-speed GPIO pin as its first instruction.
  • Measure: Measure the time delta between the trigger signal and the GPIO toggle on the oscilloscope. This delta represents the absolute worst-case hardware interrupt latency, capturing both interrupt controller (e.g., ARM GIC) delays and kernel entry overhead.

2. Trace Kernel Latency with Ftrace

When hardware measurements reveal unacceptable jitter, the Linux kernel's built-in ftrace framework helps identify software bottlenecks such as non-preemptible sections or interrupt masking.

Mount the debug filesystem to configure the tracer:

mount -t tracefs nodev /sys/kernel/tracing
cd /sys/kernel/tracing

Tracing Interrupts-Off Latency (irqsoff)

The irqsoff tracer records the longest duration for which interrupts were disabled globally:

echo irqsoff > current_tracer
echo 0 > tracing_max_latency
echo 1 > tracing_on
# Run your workload here
echo 0 > tracing_on
cat trace

The trace output reveals the exact function call that held interrupts disabled and the call stack responsible for the delay.

Monitoring Specific IRQ Events

To trace specific hardware interrupt lifecycles alongside CPU scheduling:

echo 1 > events/irq/irq_handler_entry/enable
echo 1 > events/irq/irq_handler_exit/enable
echo 1 > events/sched/sched_switch/enable

3. Record High-Resolution Traces with Trace-cmd

trace-cmd is a user-space front end for ftrace that minimizes tracing overhead on low-power SBCs.

Capture interrupt handling and scheduling events while running a workload:

trace-cmd record -e irq -e sched -e timer -R 99 -T

You can analyze the generated trace.dat file locally using trace-cmd report or visualize it graphically using KernelShark on a host development machine to view thread preemptions and interrupt handler timelines.

4. Stress Test with Cyclictest

cyclictest measures system latency under load. While it natively measures timer latency, configuring it alongside ftrace triggers an automated kernel trace dump whenever latency crosses a defined threshold.

cyclictest --smp -p 98 -m -b 1000 -d 0 -i 200 --tracemark
  • -p 98: Sets real-time priority (SCHED_FIFO).
  • -b 1000: Breaks execution and stops tracing when latency exceeds 1000 microseconds.
  • --tracemark: Writes a marker to the ftrace buffer when the threshold is violated.

5. SBC Configuration and Optimization

To achieve minimal and predictable interrupt latency, ensure the following SBC parameters are configured:

  • CPU Affinity: Bind critical hardware IRQs to a dedicated CPU core by updating /proc/irq/<IRQ_NUM>/smp_affinity.
  • Core Isolation: Use the kernel boot parameter isolcpus=<core_id> and nohz_full=<core_id> to prevent general user threads and system timers from scheduling on the core processing the critical interrupt.
  • Disable Power Management: Set the CPU frequency governor to performance (cpufreq-set -g performance) and disable dynamic C-states (idle=poll or processor.max_cstate=1 in boot arguments) to prevent CPU wake-up latency penalties.

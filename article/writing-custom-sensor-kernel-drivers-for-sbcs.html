Writing Custom Sensor Kernel Drivers for SBCs

Writing a Linux kernel device driver for a custom sensor on a single board computer (SBC) involves identifying the sensor's communication interface, selecting the appropriate kernel subsystem, describing the hardware in a Device Tree, implementing driver lifecycle and data-reading callbacks, and compiling the code into a loadable kernel module. This guide details each technical step required to connect custom sensor hardware to the Linux kernel ecosystem.

1. Analyze Hardware Specifications and Interfaces

Before writing code, review the sensor's datasheet to identify its operational parameters:

  • Bus Protocol: Most sensors use I2C, SPI, or UART. Note the default bus speed, chip addresses, and clock polarity/phase.
  • Register Map: Map out the command registers for initialization, configuration, status checks, and data output.
  • Interrupts: Determine if the sensor provides an interrupt pin (e.g., Data Ready, Threshold Alerts) and note the active logic level (high, low, edge-triggered).

2. Select the Appropriate Kernel Subsystem

Rather than writing a generic character device, use a standardized Linux kernel subsystem:

  • Industrial I/O (IIO) Subsystem: The standard choice for ADCs, DACs, accelerometers, gyroscopes, light sensors, temperature sensors, and pressure sensors. It provides built-in buffering, trigger mechanisms, and standard sysfs attributes.
  • Hardware Monitoring (hwmon): Used specifically for thermal, fan, and voltage sensors in system-health monitoring contexts.
  • Input Subsystem: Best suited for buttons, touch panels, rotary encoders, or joysticks.

3. Configure the Device Tree

SBCs using ARM or RISC-V architectures rely on the Device Tree (DT) to discover non-enumerable hardware. You must declare your sensor in a Device Tree Overlay (.dtbo) or within the main Device Tree Source (.dts):

  • Specify the Parent Bus: Attach the sensor node to the target I2C or SPI controller node.
  • Define Properties: Include the compatible string matching your driver, the reg property (I2C address or SPI chip-select), SPI clock frequencies, and interrupt lines mapped to specific GPIO pins.

4. Implement Driver Boilerplate and Probing

Set up the kernel module structure with the required license, author information, and device identification tables:

  • Matching Table: Define an of_device_id table containing the compatible string specified in your Device Tree.
  • Driver Structure: Populate an i2c_driver or spi_driver struct with pointers to probe, remove, and the device matching table.
  • Probe Function: When the kernel matches the Device Tree node to your driver, it executes the probe() function. In probe():
    1. Allocate subsystem resources (e.g., devm_iio_device_alloc).
    2. Map communication resources (such as regmap_init_i2c).
    3. Reset and initialize the sensor registers.
    4. Request and configure optional GPIO interrupt lines via devm_request_threaded_irq.
    5. Register the device with the chosen subsystem (e.g., devm_iio_device_register).
  • Remove Function: Clean up allocated resources, power down the sensor, and unregister hooks. When using resource-managed functions (the devm_* family), much of this cleanup is handled automatically.

5. Implement Subsystem Callbacks

For an IIO driver, define an iio_info structure containing callback functions:

  • read_raw: Intercepts requests when user-space reads attributes from /sys/bus/iio/devices/iio:deviceX/. Use this function to read raw sensor registers, apply scaling factors, and return processed or raw integers.
  • write_raw: Handles user-space adjustments to sampling rates, filter bandwidths, or calibration offsets.
  • Channel Specifications (iio_chan_spec): Define what channels your sensor supports (e.g., IIO_TEMP, IIO_ACCEL) along with their data types, bit depths, and storage formats.

6. Build, Deploy, and Test

  • Build Configuration: Create a Makefile pointing to the target SBC’s kernel headers or cross-compilation toolchain. Build the module using make -C /lib/modules/$(uname -r)/build M=$(PWD) modules.
  • Compile and Apply Device Tree: Compile the overlay using the Device Tree Compiler (dtc -@ -I dts -O dtb -o sensor.dtbo sensor.dts) and load it via the bootloader config or /sys/kernel/config/device-tree/overlays/.
  • Load Driver: Insert the module using insmod sensor.ko or place it in /lib/modules/ and load via modprobe.
  • Verify: Check kernel logs with dmesg to ensure successful probing. Test user-space access by reading sensor outputs from /sys/bus/iio/devices/ or via utility tools like iio-sensor-proxy and libiio.

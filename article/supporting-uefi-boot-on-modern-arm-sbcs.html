Supporting UEFI Boot on Modern ARM SBCs

Implementing UEFI boot mechanisms on modern ARM single board computers (SBCs) bridges the gap between fragmented embedded ecosystems and standardized PC-like operating system installations. This article explores the essential firmware considerations required to enable UEFI on ARM hardware, focusing on the integration of Arm Trusted Firmware (TF-A), the choice between EDK II and U-Boot implementations, Device Tree versus ACPI hardware description, non-volatile variable storage, and compliance with Arm SystemReady standards.

Arm SystemReady and Standard Compliance

When designing or porting UEFI firmware for an ARM SBC, adhering to Arm’s Base Boot Requirements (BBR) is critical. Arm defines distinct compliance bands under its SystemReady initiative:

  • SystemReady IR (IoT Ready): Requires UEFI support combined with Device Tree (DT) hardware descriptions. This is the most common target for embedded and maker SBCs.
  • SystemReady ES (Embedded Server): Requires UEFI alongside ACPI (Advanced Configuration and Power Interface) and SMBIOS, providing the closest parity to standard x86 systems.

Adherence to these profiles ensures that generic, distribution-agnostic OS installers (like Debian, Fedora, or openSUSE) can boot out-of-the-box without requiring platform-specific kernels or board support packages (BSPs).

Multi-Stage Boot and Arm Trusted Firmware (TF-A)

Unlike x86 platforms where firmware initialization is largely hidden within a proprietary UEFI PI (Platform Initialization) framework, ARM architectures rely on explicit security state segregation via Exception Levels (EL0 to EL3).

  1. BootROM (EL3 / Secure ROM): Loads the initial secondary program loader.
  2. TF-A (BL1/BL2/BL31): Initializes the Secure World, sets up the Power State Coordination Interface (PSCI), and transitions execution to EL2 (Hypervisor) or EL1 (OS/Non-secure) mode.
  3. UEFI Payload (BL33): The non-secure bootloader that provides the standard UEFI Runtime and Boot Services.

Firmware developers must ensure that PSCI is properly implemented in the secure monitor (BL31) so that the subsequent UEFI payload and the operating system can reliably control secondary CPU cores, system reset, and low-power states.

Firmware Implementation: EDK II vs. U-Boot

Developers typically choose between two primary approaches to implement UEFI:

  • Tianocore EDK II: A native, complete UEFI implementation. It provides full UEFI compliance, robust Secure Boot integration, and straightforward ACPI support. However, EDK II often requires extensive board-level hardware initialization code from scratch.
  • U-Boot with UEFI Interface: Das U-Boot includes a built-in UEFI translation layer. It leverages existing, robust peripheral drivers and Device Tree definitions already written for U-Boot while exposing the necessary UEFI Boot and Runtime Services to the operating system.

For simple consumer or development SBCs, U-Boot's UEFI subsystem is often easier to deploy, whereas EDK II is preferred for enterprise-grade or server-oriented ARM boards requiring strict ACPI and Secure Boot.

Hardware Description: Device Tree vs. ACPI

UEFI platforms traditionally rely on ACPI tables to describe system topology, power states, and devices. On ARM SBCs:

  • Device Tree passing: If targeting embedded distributions via UEFI, the firmware must pass an updated, validated Device Tree Blob (DTB) to the OS using the UEFI Configuration Table mechanism (EFI_DTB_TABLE_GUID).
  • ACPI conversion: If ACPI is required, all system peripherals, interrupt lines, PCIe root complexes, and power regulators must be mapped into DSDT/SSDT tables. This increases implementation complexity but ensures compatibility with enterprise OS releases and Windows on Arm.

UEFI Non-Volatile Variable Storage (NVRAM)

A fully compliant UEFI environment requires persistent storage for runtime and boot variables (such as BootOrder and BootNext). ARM SBCs frequently lack dedicated SPI NOR flash exclusively assigned for NVRAM.

Key variable storage strategies include:

  • SPI NOR Flash: Partitioning a region of the system's SPI flash memory to hold variable stores (e.g., via EDK II Variable driver).
  • eMMC RPMB (Replay Protected Memory Block): Utilizing the secure RPMB partition on eMMC storage. This is managed via OP-TEE (Secure World) and exposed to UEFI to guarantee tamper-resistant variable storage.
  • File-backed NVRAM: Emulating persistent variables using a file on an EFI System Partition (ESP). While functional for non-secure environments, this approach lacks cryptographic isolation and fails strict UEFI specification compliance.

Secure Boot and Key Management

Enabling UEFI Secure Boot on ARM requires establishing a hardware Root of Trust. Firmware must support:

  • Secure verification of the boot image (Authenticode/PE32+) against the UEFI signature database (db) and forbidden database (dbx).
  • Protection of the Platform Key (PK) and Key Exchange Key (KEK).
  • Integration with secure storage backends (such as OP-TEE or hardware eFuses) to prevent unauthorized key modification at runtime or physical attack vectors.

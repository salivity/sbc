Reduce Boot Time on Single Board Computers

Reducing boot latency on single board computers (SBCs) requires a systematic approach to streamlining the boot pipeline, from hardware initialization to user-space execution. This guide outlines the most effective techniques to achieve sub-second to low-second application launch times by optimizing the bootloader, stripping down the Linux kernel, minimizing the init system, and tuning the root filesystem.

1. Optimize the Bootloader

The default bootloader (such as U-Boot) often spends unnecessary seconds waiting for user input, checking network interfaces, or initializing unused hardware.

  • Set the Boot Delay to Zero: Configure bootdelay=0 in the environment variables to eliminate the countdown timer for user interruption.
  • Disable Unused Features: Recompile the bootloader without support for unused storage devices, network stacks, USB controllers, and verbose debugging messages.
  • Enable U-Boot Falcon Mode: Falcon Mode allows the bootloader to load and jump directly to the Linux kernel, completely skipping the second stage of U-Boot.

2. Streamline the Linux Kernel

A generic Linux distribution kernel contains hundreds of unused drivers and features that slow down the initialization process.

  • Compile a Minimal Custom Kernel: Remove all drivers, protocols, and subsystems not required by your specific board and application.
  • Build Critical Drivers Statically: Eliminate the need for an initial RAM filesystem (initramfs) by compiling essential storage, bus, and display drivers directly into the kernel image (built-in).
  • Optimize Kernel Compression: Use faster decompression algorithms like LZ4 or LZO instead of GZIP or XZ. While the image size is slightly larger, decompression speeds on low-power CPUs are significantly faster.
  • Silence Kernel Logging: Pass quiet, loglevel=0, and console= to the kernel command line (bootargs) to eliminate serial console output bottlenecks during boot.

3. Bypass or Optimize the Init System

Standard user-space init systems like systemd add significant latency by running dependency checks and launching non-essential background services.

  • Direct Application Execution (init=/path/to/app): For dedicated appliances, bypass the init system entirely by pointing the kernel's init= boot argument directly to your binary or a minimal shell script.
  • Use a Lightweight Init: If a full init system is required, replace systemd with BusyBox init or runit.
  • Audit systemd Services: If systemd cannot be replaced, use systemd-analyze blame and systemd-analyze critical-chain to identify slow services, then disable or mask unnecessary units like network managers, bluetooth, and logging daemons.

4. Optimize the Root Filesystem and Storage

Slow read operations on secondary storage can introduce noticeable application launch delays.

  • Use High-Speed Media: Prefer onboard eMMC or NVMe SSDs over standard MicroSD cards, as they offer substantially higher random read speeds and lower access times.
  • Use Read-Only or Compressed Filesystems: SquashFS or EROFS provide fast, compressed read-only filesystems that reduce the physical amount of data read from storage during boot.
  • Defer Non-Critical File Mounting: Mount secondary filesystems, network shares, and writable partitions asynchronously in the background after the primary application has launched.

5. Tune Application Startup

Optimizing how the application binary is built and initialized prevents user-space delays.

  • Static Linking: Link core libraries statically to eliminate runtime dynamic linker resolution overhead.
  • Lazy Initialization: Refactor the application to render the initial user interface or core logic immediately, deferring background tasks, network discovery, and secondary assets until after startup.

How to Benchmark Memory Latency and Cache on SBCs

Benchmarking memory latency and cache performance on multi-tier single board computers (SBCs) involves profiling the data transfer speeds and access delays across the entire memory hierarchy, from L1/L2/L3 CPU caches to off-chip system RAM. Because modern SBCs often feature asymmetric core architectures (such as ARM big.LITTLE) and complex memory buses, developers must utilize specialized microbenchmarking tools, hardware performance counters, and strict core isolation techniques to accurately measure nanosecond-level latencies and identify memory bottlenecks.

1. Account for Asymmetric Multi-Core Architectures

Modern multi-tier SBCs frequently combine high-performance cores with energy-efficient cores, each featuring distinct L1 and L2 cache sizes and clock speeds.

  • CPU Frequency Scaling: Lock the CPU frequency governor to performance mode before running tests to prevent dynamic voltage and frequency scaling (DVFS) from skewing latency measurements.
  • Core Affinity (taskset): Bind benchmarking processes to specific CPU cores using taskset or numactl. This ensures that performance measurements are isolated to either the high-performance cluster or the efficiency cluster, preventing threads from migrating mid-test.

2. Utilize Pointer Chasing for Latency Profiling

Hardware prefetchers can artificially lower apparent memory latency during sequential access. To measure true access latency, developers use pointer-chasing algorithms where each memory read contains the address of the next read in a randomized array.

  • LMbench (lat_mem_rd): The standard tool for mapping cache hierarchies. By varying the array size from a few kilobytes (fitting into L1 cache) to hundreds of megabytes (spilling into system RAM), LMbench generates step graphs that clearly indicate the capacity limits and access latencies of L1, L2, L3 (if present), and main DDR memory.
  • Tinymembench: An embedded-focused microbenchmark that measures both memory bandwidth (using various memcpy and memset implementations) and random access latency across different buffer sizes.

3. Measure Hardware Counters with Linux perf

To understand how real applications interact with the memory subsystem, developers rely on the Linux perf subsystem to monitor on-chip Performance Monitoring Units (PMUs).

  • Cache Miss Monitoring: Execute commands such as perf stat -e L1-dcache-load-misses,L1-dcache-loads,l2d_cache_refill,bus_access alongside your workload to quantify how frequently data requests fail to hit the cache tiers.
  • Instruction-Level Profiling: Use perf record and perf report to pinpoint specific lines of code or data structures causing high cache miss ratios or pipeline stalls due to memory waiting times.

4. Evaluate Shared Memory and Inter-Core Latency

In multi-tier SBCs, memory latency is also influenced by inter-core communication and cache-coherency protocols across different CPU clusters.

  • Core-to-Core Latency: Benchmarks such as core-to-core-latency measure the time required to pass a cache line between two cores via shared caches or the interconnect.
  • Bus Contention Testing: Run memory-heavy tasks on background cores while benchmarking latency on a target core to measure how memory bus contention degrades overall access times under realistic multi-threaded loads.

5. Analyzing the Output

A standard latency-versus-working-set-size plot will display distinct "steps":

  • L1 Cache: Lowest latency (typically 1–2 ns).
  • L2 Cache: Mid-tier latency (typically 3–10 ns).
  • L3/System Cache: Higher latency before reaching off-chip memory.
  • Main DDR Memory: Highest latency plateau (typically 60–120+ ns on standard SBCs).

Identifying the exact memory footprint where latency jumps allows developers to optimize data structures, cache alignment, and buffer sizes to fit entirely within the fastest available tier of the SBC's memory architecture.

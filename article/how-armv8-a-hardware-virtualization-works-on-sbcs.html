How ARMv8-A Hardware Virtualization Works on SBCs

Hardware-level virtualization on an ARMv8-A architecture Single Board Computer (SBC) enables multiple operating systems to run concurrently on a single physical board with near-native performance. This is achieved through dedicated silicon-level extensions that provide hardware-enforced CPU privilege separation, two-stage memory translation, and direct virtualization of system interrupts and timers. By offloading resource isolation and context switching from software to the ARM core itself, the system minimizes virtualization overhead on resource-constrained SBC platforms.

Exception Levels and CPU Privilege Separation

The foundation of ARMv8-A virtualization is its privilege hierarchy, known as Exception Levels (EL):

  • EL0: Unprivileged application execution.
  • EL1: Operating system kernel mode (Guest OS).
  • EL2: Hypervisor mode.
  • EL3: Secure Monitor and firmware (TrustZone).

In standard execution, an OS kernel runs in EL1. In a virtualized setup, the hypervisor operates in EL2. EL2 provides dedicated control registers that allow the hypervisor to configure, isolate, and intercept operations from multiple EL1 guest instances without modifying the guest kernels.

Two-Stage Memory Translation (Stage-2 MMU)

ARMv8-A uses a two-stage Memory Management Unit (MMU) to isolate memory spaces among guest systems:

  1. Stage-1 Translation (Guest Control): The guest operating system at EL1 translates its own Virtual Addresses (VA) to what it assumes are Physical Addresses, referred to as Intermediate Physical Addresses (IPA).
  2. Stage-2 Translation (Hypervisor Control): The hardware MMU takes the IPA and translates it to the actual Physical Address (PA) on the SBC’s RAM using translation tables configured by the hypervisor at EL2.

This two-stage process happens entirely in hardware, ensuring memory isolation between different virtual machines without requiring the hypervisor to intercept every memory access.

Hardware Interrupt Virtualization via ARM GIC

Interrupt handling is handled by the ARM Generic Interrupt Controller (typically GICv2, GICv3, or GICv4 on ARMv8-A SBCs). The GIC features hardware virtualization extensions:

  • Virtual CPU Interface: The hypervisor configures the physical interrupt controller and routes specific interrupts to virtual machines.
  • List Registers: The hypervisor writes pending virtual interrupts into dedicated hardware List Registers.
  • Direct Guest Acknowledgment: The guest OS at EL1 can signal and clear interrupts directly through its virtual CPU interface without trapping back into EL2, significantly reducing CPU cycles and latency.

Instruction Trapping and Emulation

When a guest OS in EL1 attempts to perform sensitive actions—such as modifying system control registers, configuring hardware clocks, or accessing restricted peripheral memory—the ARMv8-A core triggers a trap exception to EL2.

The hypervisor intercepts the trapped instruction, emulates the expected hardware behavior or translates the access to an assigned virtual device, and resumes execution of the guest OS.

System Timers and I/O Virtualization

ARMv8-A includes dedicated hardware timers for virtualization:

  • Virtual Timers: Dedicated per-core registers allow the guest OS to read time and configure timer interrupts without EL2 intervention.
  • Hypervisor Timers: Separate timers exist solely for the hypervisor to enforce CPU time-slicing and scheduling between guest instances.

For peripheral I/O, SBCs rely on software emulation (like VirtIO via KVM) or hardware-assisted direct assignment through an optional System MMU (SMMU), allowing high-throughput devices such as PCIe controllers or Ethernet interfaces to be safely passed directly to a guest machine.

Boot Sequence on SBC Hardware

For virtualization to function on an ARMv8-A SBC:

  1. Low-level firmware (such as ARM Trusted Firmware) initializes the board and executes in EL3.
  2. The bootloader (such as U-Boot or EDK2) drops execution to non-secure EL2 before loading the Linux kernel.
  3. If booted in EL2, the host OS kernel initializes the KVM (Kernel-based Virtual Machine) subsystem, granting it full control over the ARMv8-A hardware virtualization features.

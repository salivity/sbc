WireGuard VPN Setup for Remote SBC Fleets

Establishing secure point-to-point WireGuard tunnels across a fleet of field-deployed single board computers (SBCs) requires a systematic approach to key generation, configuration management, NAT traversal, and lifecycle automation. Because SBCs often operate on cellular networks or behind restrictive firewalls, standard point-to-point connections rely on automated provisioning tools, a central rendezvous or coordination server, and persistent connection configurations. This guide details the practical architecture and deployment steps developers use to securely manage WireGuard connections across distributed edge devices.

1. Network Topology and Architecture

While WireGuard is strictly a point-to-point protocol, managing a fleet requires choosing between two primary topologies:

  • Hub-and-Spoke: Each SBC establishes a tunnel to a centralized cloud gateway (hub) with a static public IP. Routing rules on the hub allow SBCs to communicate with central services or with other nodes via the hub. This is the most reliable setup for edge hardware behind NAT.
  • Full Mesh with Coordination: SBCs connect directly to one another using a control plane (such as Headscale or custom signaling APIs) to negotiate dynamic IP changes and hole-punching.

For most production fleets, the hub-and-spoke model is preferred due to its simplicity, predictable firewall behavior, and centralized access control.

2. Automated Key Generation and Management

Security relies on unique cryptographic key pairs for every device. Never bake private keys into a master operating system image.

  1. First-Boot Key Generation: Configure a first-boot script (using cloud-init, systemd, or custom provisioning daemons) to run wg genkey | tee privatekey | wg pubkey > publickey.
  2. Secure Storage: Restrict permissions on the private key file immediately (chmod 600 privatekey). On SBCs with cryptographic hardware (such as TPM 2.0 or ATECC608 chips), store keys within the secure element.
  3. Public Key Registration: The SBC sends its public key, along with its unique device ID and an authentication token, to a central fleet management API via HTTPS. The API assigns a dedicated tunnel IP address (e.g., 10.100.0.x/32) and registers the peer on the central WireGuard gateway.

3. Configuring NAT Traversal and Endpoints

Field SBCs commonly use 4G/5G modems or restricted local Wi-Fi, meaning they do not possess public IPv4 addresses. To keep the tunnel open through firewalls and stateful NAT routers:

  • Specify Central Endpoint: Set the Endpoint in the SBC's wg0.conf to the domain or static IP of the central gateway.
  • Enable Persistent Keepalive: Include PersistentKeepalive = 25 inside the [Peer] section of the SBC configuration. This instructs WireGuard to send an empty packet every 25 seconds, keeping the NAT mapping active in the carrier's gateway.

Example SBC Configuration (/etc/wireguard/wg0.conf):

[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY>
Address = 10.100.0.15/24
DNS = 1.1.1.1

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.100.0.0/24
PersistentKeepalive = 25

4. Fleet Provisioning and Configuration Deployment

Manual configuration does not scale. Developers use configuration management tools to automate deployment:

  • Ansible / SaltStack: For connected devices, use dynamic inventory plugins to push updated peer lists and configurations.
  • Containerized Deployments (Docker / Balena): Run WireGuard inside a lightweight container with NET_ADMIN capabilities. The container entrypoint script can query the fleet management API on startup, retrieve the latest assigned network parameters, and launch wg-quick.
  • Template Engines: Use tools like envsubst or Jinja2 templates in your initialization pipeline to generate the wg0.conf file dynamically using environment variables provided during device flashing.

5. Tunnel Persistence and Failure Recovery

Field devices experience frequent power loss, intermittent connectivity, and cellular dropouts. Implement robust service management to maintain connectivity:

  • Systemd Service: Enable the built-in WireGuard systemd unit: 
    systemctl enable wg-quick@wg0.service
  • Connection Watchdog: Deploy a lightweight health check script via a cron job or systemd timer. The script pings the central gateway (e.g., 10.100.0.1). If the ping fails consecutively for several minutes, the script restarts the interface using wg-quick down wg0 && wg-quick up wg0 or reinitializes the network interface.
  • Dynamic DNS Handling: If the central gateway uses dynamic DNS instead of a static IP, install reresolve-dns scripts to ensure the SBC updates the endpoint IP when the gateway's DNS record changes without requiring a full service restart.

Software Requirements for Kubernetes on SBC Nodes

Running a Kubernetes cluster across a fleet of Single Board Computers (SBCs)—such as Raspberry Pi, Orange Pi, or Rockchip-based boards—requires a resource-conscious software stack optimized for ARM architectures. Because SBCs typically have limited CPU, memory, and I/O throughput compared to traditional enterprise servers, choosing lightweight, compatible software components is critical. This guide outlines the essential operating systems, container runtimes, Kubernetes distributions, networking plugins, and kernel prerequisites necessary to deploy and maintain a stable SBC Kubernetes cluster.

1. 64-Bit Operating System (OS)

A 64-bit Linux distribution (ARM64/aarch64) is strongly recommended for running modern Kubernetes clusters, as many container images and Kubernetes binaries have deprecated or limited 32-bit (ARMv7/armhf) support.

  • Ubuntu Server (64-bit): Widely supported, with official builds available for most popular SBCs and extensive documentation.
  • Debian / Raspberry Pi OS (64-bit Lite): Minimal resource footprint, ideal for low-memory nodes.
  • Armbian: Optimized for diverse, non-Raspberry Pi ARM boards (e.g., Allwinner, Rockchip).
  • Alpine Linux: Ultra-lightweight distribution for environments where RAM conservation is the top priority.

2. Kernel and System Configuration

Before installing Kubernetes, the underlying operating system kernel requires specific parameters and modules to be enabled:

  • Control Groups (cgroups): Memory and CPU cgroups must be enabled to allow Kubernetes to limit and isolate container resources. On Debian/Ubuntu systems, this is typically enabled via boot flags: 
    cgroup_enable=cpuset cgroup_enable=memory cgroup_memory=1
  • Swap Management: Memory swap must be disabled across all nodes (swapoff -a), as Kubernetes' scheduler assumes memory allocation guarantees that swap can disrupt.
  • Kernel Modules: Essential networking modules must load on boot, specifically overlay and br_netfilter.
  • Sysctl Configurations: Network packet forwarding must be explicitly permitted: 
    net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1

3. Lightweight Kubernetes Distributions

Standard Kubernetes (kubeadm) can be heavy on resources, often consuming 1 GB to 2 GB of RAM on control plane nodes. Purpose-built lightweight distributions are better suited for SBC fleets:

  • K3s: A CNCF-certified, highly lightweight distribution packaged as a single binary. It reduces memory usage by replacing etcd with SQLite (or external DBs) for single-node control planes, stripping out legacy cloud providers, and bundling required components.
  • k0s: A zero-friction, single-binary Kubernetes distribution with minimal system dependencies and flexible control-plane separation.
  • MicroK8s: An enterprise-grade, low-overhead Kubernetes distribution managed via Snap packages, optimized for edge computing and IoT hardware.

4. Container Runtime Interface (CRI)

Kubernetes requires an Open Container Initiative (OCI)-compliant runtime to manage container lifecycles:

  • containerd: The industry-standard CRI, offering high performance and low overhead. Often pre-bundled with K3s and MicroK8s.
  • CRI-O: A lightweight alternative designed exclusively to implement the Kubernetes CRI specification without unnecessary tooling.

5. Container Network Interface (CNI)

Networking on SBC clusters must balance feature sets with CPU and memory consumption:

  • Flannel: The default choice for lightweight setups. Uses VXLAN or host-gw backends, consuming minimal CPU cycles.
  • Calico: Provides advanced Network Policy enforcement and BGP routing, though it demands slightly more memory per node.
  • Cilium: Suitable for higher-end SBCs (e.g., RK3588 with 8GB+ RAM) that support modern eBPF kernels, providing fast datapaths and security monitoring.

6. Lightweight Storage (CSI)

Because SBCs often rely on SD cards or USB storage, persistent volume provisioners must minimize write amplification to prevent media degradation:

  • Local Path Provisioner: Utilizes local directories on each node for hostPath-backed persistent volumes with minimal overhead.
  • Longhorn: Provides distributed block storage, though it requires robust network bandwidth (Gigabit Ethernet) and adequate RAM across nodes.
  • NFS Subdir External Provisioner: Offloads storage I/O from the SBC fleet to a centralized Network-Attached Storage (NAS) device.

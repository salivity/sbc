Real-Time Linux on Single Board Computers

Deploying a real-time Linux kernel—typically patched with PREEMPT_RT—on a Single Board Computer (SBC) enables deterministic, low-latency task execution for robotics, industrial control, and data acquisition. However, transforming a low-cost, general-purpose SBC into a reliable real-time system requires managing hardware constraints, power configurations, memory bottlenecks, and kernel settings to prevent unexpected latency spikes.

Hardware Constraints and Driver Compatibility

Most SBCs are designed for multimedia and general-purpose computing rather than strict determinism. Many peripheral drivers (such as Wi-Fi, GPU, or proprietary camera interfaces) rely on closed-source binary blobs or poorly optimized Interrupt Service Routines (ISRs). In a real-time kernel, non-deterministic drivers can block preemption, creating massive latency spikes. It is essential to use open-source drivers where code execution paths are clear, or disable non-essential peripheral drivers entirely.

CPU Frequency Scaling and Power Management

Power-saving mechanisms are major sources of jitter in embedded Linux systems.

  • Dynamic Voltage and Frequency Scaling (DVFS): When the CPU transitions between frequency states, execution halts momentarily. Setting the CPU governor to performance ensures consistent clock frequencies.
  • CPU Idle States (C-States): Deep sleep states introduce wake-up latency when an interrupt occurs. Disabling deep C-states via kernel command-line parameters (such as idle=poll or processor.max_cstate=1) preserves fast interrupt response times.
  • Thermal Throttling: SBCs without active cooling can overheat quickly under sustained loads. When the thermal limit is reached, hardware-level throttling reduces CPU frequency independently of the operating system, degrading real-time performance.

Memory Latency and Cache Contention

Standard dynamic memory allocation and memory swapping introduce unpredictable delays.

  • Memory Locking: Real-time applications must lock their memory space into physical RAM using system calls like mlockall() to prevent page faults during critical execution phases.
  • Cache Sharing: Multi-core SBC processors generally share L2 or L3 caches. Non-real-time processes can evict critical real-time data from the cache. Employing Cache Allocation Technology (CAT) where supported, or minimizing background memory traffic, mitigates this issue.
  • Storage I/O: Standard SD card and eMMC write cycles have unpredictable latency profiles. Logging directly to flash storage during real-time loops must be avoided by buffering logs in RAM or utilizing network-based logging.

Core Isolation and Interrupt Balancing

To ensure deterministic execution, real-time tasks should not compete with standard operating system services.

  • Core Isolation: Use the isolcpus kernel parameter to reserve dedicated CPU cores exclusively for real-time threads.
  • IRQ Affinity: By default, hardware interrupts are distributed across all cores. Route standard hardware interrupts away from dedicated real-time cores using smp_affinity settings or the irqbalance daemon.
  • Threaded Interrupts: Under PREEMPT_RT, interrupt handlers run as schedulable kernel threads, allowing developers to prioritize critical hardware interrupts above standard kernel tasks.

Latency Benchmarking

Average throughput is irrelevant in real-time computing; worst-case execution time (WCET) is the critical metric. Systems must be tested using tools like cyclictest under simulated maximum load (using utilities like stress-ng or heavy I/O transfers). A system is only validated once the worst-case latency stays strictly within the application's defined deadline across prolonged testing cycles.

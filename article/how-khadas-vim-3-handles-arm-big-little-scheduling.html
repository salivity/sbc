How Khadas VIM3 Handles ARM big.LITTLE Scheduling

This article provides an overview of how the Khadas VIM3 single board computer manages multi-core ARM big.LITTLE processing. It details the underlying hardware layout of the Amlogic A311D processor, the role of Linux Energy Aware Scheduling (EAS), Per-Entity Load Tracking (PELT), Dynamic Voltage and Frequency Scaling (DVFS), and how the operating system dynamically balances computational load with energy efficiency across asymmetric CPU clusters.

The Hardware Topology

The Khadas VIM3 is powered by the Amlogic A311D system-on-chip (SoC), which implements an asymmetric ARM multi-core configuration:

  • "big" Cluster: 4x ARM Cortex-A73 cores designed for high-throughput, compute-intensive workloads running at clock speeds up to 2.2 GHz.
  • "LITTLE" Cluster: 2x ARM Cortex-A53 cores optimized for power efficiency and lower-intensity background tasks running at clock speeds up to 1.8 GHz.

Both clusters reside on the same chip and share a coherent memory subsystem via ARM's cache-coherent interconnect, allowing seamless thread migration without needing to flush cache lines to main RAM.

Energy-Aware Scheduling (EAS)

The Linux kernel running on the Khadas VIM3 utilizes Energy-Aware Scheduling (EAS) instead of the standard Completely Fair Scheduler (CFS) topology. EAS integrates performance-capacity models with energy-consumption models to make intelligent task-placement decisions.

Instead of simply aiming to distribute tasks evenly across all available cores, EAS predicts the energy cost of running a given thread on either the Cortex-A53 or Cortex-A73 cluster. It then assigns the thread to the core that provides sufficient compute capacity while consuming the least amount of energy.

Per-Entity Load Tracking (PELT)

To make scheduling decisions, the kernel continuously calculates the computational requirements of every active process using Per-Entity Load Tracking (PELT).

  • Load History: PELT breaks time into 1024-microsecond windows, forming a moving average of a task's CPU utilization and execution frequency.
  • Capacity Invariance: The scheduler normalizes load metrics based on current CPU frequency and core architecture. A 50% load on a Cortex-A53 core is scaled proportionally so the scheduler understands its true footprint relative to a Cortex-A73 core.

Dynamic Task Placement and Migration

When a thread wakes up or is spawned on the Khadas VIM3, the scheduler executes the following placement routine:

  1. Light and Background Tasks: Tasks with low utilization metrics (such as I/O polling, system daemons, and basic UI rendering) are assigned to the Cortex-A53 cores. This prevents high-performance cores from spinning up unnecessarily.
  2. Demanding Workloads: When a task's tracked load exceeds the processing capacity of the Cortex-A53 cluster, the scheduler triggers a migration, moving the task to an available Cortex-A73 core.
  3. Dynamic Preemption and Fallback: If high-priority workloads saturate the "big" cores, lower-priority threads are temporarily throttled or pushed back to the "LITTLE" cores to maintain system responsiveness.

DVFS and Schedutil Governor Integration

Scheduling on the VIM3 is tightly coupled with Dynamic Voltage and Frequency Scaling (DVFS) through the schedutil CPUFreq governor.

Because schedutil has direct access to the scheduler's PELT data, it adjusts the operational voltage and clock frequencies of the CPU clusters instantly when a task is scheduled or migrated. If a bursty task moves to a Cortex-A73 core, schedutil immediately ramps up that cluster's frequency. Once the task finishes or returns to a dormant state, the governor drops the frequency or allows the core to enter low-power C-states.

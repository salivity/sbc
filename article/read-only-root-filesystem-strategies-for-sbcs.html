Read-Only Root Filesystem Strategies for SBCs

Deploying single board computers (SBCs) in the field requires high reliability against sudden power loss and flash storage degradation. A read-only root filesystem prevents filesystem corruption, eliminates SD card and eMMC write wear, and bolsters security against unauthorized tampering. This guide covers the standard architectural patterns used to implement read-only root filesystems on Linux-based embedded hardware.

1. OverlayFS with a RAM-Based Write Layer

The most common approach for general-purpose distributions (such as Debian, Ubuntu, or Raspberry Pi OS) is combining the read-only lower filesystem with a writable upper layer using OverlayFS.

  • How it works: The physical storage is mounted read-only (lowerdir). A temporary filesystem (tmpfs) in RAM serves as the writable layer (upperdir). When applications write files, they write to RAM without altering the underlying storage.
  • Pros: Complete compatibility with standard Linux distributions and software that expects a writable root filesystem.
  • Cons: Changes are lost upon reboot unless explicitly synchronized to a separate persistent partition. RAM usage increases as files are modified or created.

2. Kernel Command-Line and /etc/fstab Read-Only Mounting

The simplest native Linux strategy involves configuring the operating system to mount the root block device in read-only mode during boot.

  • How it works: The kernel boot parameter ro is passed, and /etc/fstab is configured with the ro option for the root mount point (/).
  • Implementation requirements: Standard volatile directories—such as /tmp, /var/log, /var/run, and /var/lock—must be mapped to tmpfs mounts or symlinked to /run.
  • Pros: Minimal configuration overhead with no complex overlay setup.
  • Cons: Legacy or poorly configured daemon processes that expect hardcoded writable paths in /etc or /var/lib may fail to start.

3. SquashFS with Read-Only Block Devices

For specialized embedded systems built using Yocto Project or Buildroot, utilizing an inherently read-only filesystem like SquashFS is a standard industry practice.

  • How it works: The root filesystem is compressed into a static, read-only SquashFS image written directly to a flash storage partition.
  • Pros: Significantly smaller storage footprint, fast boot times, and hardware-enforced immutability.
  • Cons: Updating the operating system requires reflashing the whole partition image rather than updating individual packages.

4. Full Initramfs Execution (RAM Root)

In applications with small footprints and sufficient system memory, the entire operating system can be loaded directly into RAM at boot.

  • How it works: The bootloader loads the kernel and a complete initramfs archive containing the root filesystem into system memory. The storage medium is unmounted immediately after boot.
  • Pros: Zero disk operations occur during runtime, completely eliminating flash storage degradation. The physical media can even be safely removed while the system is running.
  • Cons: Storage capacity is strictly limited by the SBC's available RAM.

Managing Persistent Data and Updates

A fully read-only deployment typically requires specific mechanisms to retain operational data and handle updates:

  • Dedicated Data Partitions: Create a separate, writable partition (ext4, F2FS, or UBIFS) mounted at a path such as /data to store logs, telemetry, and device-specific state.
  • A/B Dual-Partition Updates: Combine read-only root filesystems with an A/B partition scheme. Firmware updates are written atomically to the inactive partition and verified before switching boot priority, ensuring failsafe rollback capabilities.

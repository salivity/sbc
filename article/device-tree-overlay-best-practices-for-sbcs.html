Device Tree Overlay Best Practices for SBCs

This article provides a concise guide on structuring Device Tree Overlays (DTOs) for custom hardware expansions on Single Board Computers (SBCs). You will learn how to organize source files, define pin control states, maintain modularity, handle dynamic parameters, and ensure safe integration with the base system device tree.

1. Maintain Modularity per Peripheral

Create separate overlay files for distinct hardware modules rather than combining unrelated peripherals into a single monolithic file.

  • Isolate functions: If your board contains an I2C sensor, an SPI display, and a dedicated PWM driver, create three separate .dts files (e.g., custom-sensor.dts, custom-display.dts).
  • Ease troubleshooting: Independent overlays allow you to load, unload, and debug individual hardware modules without affecting others.

2. Follow Standard Overlay Syntax

Ensure the overlay source is correctly marked for dynamic application by including the proper header directives and target references.

  • Declare plugin mode: Always start the file with /dts-v1/; followed by /plugin/;.
  • Use phandle references: Target base tree nodes using references (target = <&i2c1>; or target = <&spi0>;) instead of hardcoded paths whenever possible. This ensures portability across kernel revisions.
/dts-v1/;
/plugin/;

/ {
    compatible = "brcm,bcm2835", "allwinner,sun8i-h3";

    fragment@0 {
        target = <&i2c1>;
        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;
            status = "okay";

            custom_sensor: sensor@48 {
                compatible = "vendor,sensor-model";
                reg = <0x48>;
                status = "okay";
            };
        };
    };
};

3. Define Explicit Pin Multiplexing (pinctrl)

Avoid relying on default bootloader pin states. Explicitly declare pin control and multiplexing configurations inside the overlay.

  • Group pins by function: Define dedicated pinctrl nodes for your hardware interface (e.g., GPIO interrupts, I2C, SPI lines).
  • Assign pull-up/pull-down states: Clearly define the electrical characteristics (e.g., bias pull-up, bias pull-down, or drive strength) in the pin controller configuration node.
  • Link states to peripherals: Attach the pin configuration to the target peripheral node using pinctrl-names = "default"; and pinctrl-0 = <&custom_pins>;.

4. Manage Node Status and Conflicts

  • Enable base buses: Always set status = "okay"; on the parent controller (such as &i2c1 or &spi0) within the overlay to guarantee the bus driver initializes.
  • Avoid resource collision: Check that the GPIOs, interrupts, and DMA channels you assign do not conflict with existing base system functions or other active overlays.

5. Expose Dynamic Runtime Parameters

Make your overlays adaptable by exposing parameters that can be configured at boot time without modifying the source code.

  • Use the __overrides__ node (supported by many standard bootloaders such as U-Boot and Raspberry Pi bootloader) to expose settings like I2C addresses, GPIO pin assignments, or clock speeds.
__overrides__ {
    addr = <&custom_sensor>, "reg:0";
    gpiopin = <&custom_pins>, "pins:0";
};

6. Compilation and Symbol Preservation

  • Generate symbols: When compiling the overlay with the Device Tree Compiler (dtc), always use the @ flag to generate and resolve dynamic symbol references: 
    dtc -@ -I dts -O dtb -o custom-hardware.dtbo custom-hardware.dts
  • Verify against standard schema: Use kernel tools such as dt-validate and standard yaml bindings to ensure your device tree node properties conform to Linux kernel upstream standards.

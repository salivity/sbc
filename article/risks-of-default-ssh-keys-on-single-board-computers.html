Risks of Default SSH Keys on Single Board Computers

Single-board computers (SBCs) like the Raspberry Pi, BeagleBone, and Orange Pi are widely deployed in edge computing, IoT solutions, and enterprise environments. Leaving default SSH keys active on a deployed SBC creates severe security vulnerabilities, exposing systems to unauthorized remote access, automated botnet recruitment, traffic interception, and lateral network pivoting. This article breaks down the direct security risks associated with default SSH keys and provides immediate steps to secure your deployment.

Understanding Default SSH Keys on SBCs

When operating system images are pre-flashed onto SBC storage media (like SD cards or eMMC modules), they often include pre-generated SSH host keys or pre-configured authorized_keys files. Because these keys originate from a shared, static image, every device flashed with that image shares the identical cryptographic identity unless they are regenerated upon initial boot.

Major Security Risks

1. Cryptographic Impersonation and Man-in-the-Middle (MitM) Attacks

SSH host keys prove the identity of the server to the connecting client. If your SBC uses a default host key that is publicly known or extracted from a standard firmware image:

  • Attackers can impersonate your SBC on the network.
  • Clients connecting to the device will accept the attacker's forged server without receiving an SSH host key verification warning.
  • Attackers can decrypt, read, and manipulate SSH traffic, capturing administrative commands, passwords, and sensitive transmitted data.

2. Immediate Unauthorized Remote Access

Some development OS images ship with pre-baked public keys in the ~/.ssh/authorized_keys file for default users (such as pi, root, or admin), paired with a publicly accessible private key.

  • Anyone possessing the known private key can immediately authenticate to the SBC via SSH without a password.
  • Attackers obtain root or user-level shell privileges instantly upon locating the device online.

3. Automated Scanning and Botnet Enlistment

Malicious actors deploy automated scripts and worms that constantly scan the public IPv4 and IPv6 address spaces for open SSH ports (port 22).

  • These scanners test known SSH key pairs extracted from popular vendor SBC images and firmware repositories.
  • Vulnerable devices are compromised within minutes of connecting to the internet and are typically enrolled into distributed denial-of-service (DDoS) botnets or cryptocurrency mining networks.

4. Lateral Movement and Internal Network Pivoting

SBCs are frequently placed on local networks behind firewalls to act as gateways, automation controllers, or sensor hubs.

  • Once an attacker gains access via default SSH credentials, the compromised SBC acts as an internal bridgehead.
  • Attackers bypass perimeter firewalls to scan internal subnets, compromise other network devices, and exfiltrate internal data.

5. Firmware and Device Tampering

With persistent SSH access, attackers can modify boot configurations, install rootkits, manipulate GPIO pin actions, alter sensor readings, or flash malicious firmware. In industrial or critical infrastructure contexts, this can lead to physical equipment damage or safety hazards.

Essential Remediation Steps

Securing an SBC requires clearing static identity files and generating unique cryptographic material prior to deployment:

  • Regenerate SSH Host Keys: Delete existing keys and generate new ones during the initial setup script or first boot: 
    sudo rm /etc/ssh/ssh_host_*
sudo dpkg-reconfigure openssh-server
sudo systemctl restart ssh
  • Audit Authorized Keys: Clear any pre-existing keys in ~/.ssh/authorized_keys and add only your own freshly generated public keys.
  • Disable Root and Password Logins: Restrict remote root access and enforce key-based authentication by updating /etc/ssh/sshd_config: 
    PermitRootLogin no
PasswordAuthentication no
  • Change Default User Accounts: Remove or rename default vendor accounts and set strong, unique passwords.

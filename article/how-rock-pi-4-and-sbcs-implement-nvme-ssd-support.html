How Rock Pi 4 and SBCs Implement NVMe SSD Support

This article explores how single-board computers (SBCs) like the Rock Pi 4 implement support for high-speed NVMe M.2 solid-state drives. It examines the hardware integration of PCIe lanes from the main processor, the physical interface and power delivery mechanisms, and the low-level software and firmware configurations required to detect, run, and boot from NVMe storage devices.

Native PCIe Lane Integration from the SoC

The foundation of NVMe support on modern developer boards is the System-on-Chip (SoC). Boards like the Rock Pi 4 utilize processors such as the Rockchip RK3399, which feature integrated PCI Express (PCIe) controllers. The RK3399 natively provides a PCIe 2.1 interface with up to four lanes (x4), offering bidirectional bandwidth of up to 2 GB/s. Instead of routing storage through slower USB-to-SATA bridge chips or shared buses, the board connects the PCIe signals directly from the SoC's PHY (physical layer) pins to the storage subsystem.

Physical Interfaces and M.2 Form Factors

To connect standard M.2 NVMe drives, developer boards must expose the PCIe signals through a compatible physical connector. The Rock Pi 4 implements this in two main ways depending on the hardware revision:

  • Dedicated Onboard Connectors: Certain models feature a standard M.2 M-Key slot mounted directly to the bottom of the PCB. This slot accommodates common SSD sizes such as 2280 (22mm x 80mm) or 2230.
  • High-Density FPC/Ribbon Extensions: To maintain a compact form factor (the standard Raspberry Pi layout), some boards use a flat flexible cable (FFC) connector on the board that routes PCIe lanes to an add-on board, such as an M.2 Extension HAT.

The connector is wired according to the M.2 M-Key specification, which designates four PCIe lanes, differential clock lines (REFCLK), reset signals (PERST#), and device detection pins.

Power Delivery Architecture

M.2 NVMe SSDs require a dedicated 3.3V power rail and can draw significant peak currents (often between 2.5A and 3.5A during heavy read/write operations). Because standard SBC power supplies input 5V, 9V, or 12V via USB Type-C or DC barrel jacks, the board or its extension HAT incorporates dedicated step-down (buck) voltage regulators. These regulators ensure a stable 3.3V supply to the M.2 slot to prevent drive dropouts, data corruption, or system brownouts under heavy I/O loads.

Linux Kernel and Device Tree Support

Once the hardware connection is established, the operating system interacts with the drive using standard Linux subsystems:

  1. Device Tree (.dts): The board's device tree source file defines the PCIe controller properties, including memory-mapped I/O ranges, interrupt lines, clock sources, and power supply regulators (vpcie3v3). This informs the kernel how to initialize the PCIe controller on boot.
  2. Kernel Drivers: Linux includes native support for both the Rockchip PCIe controller driver (pcie-rockchip-host) and the standard NVMe block driver (CONFIG_BLK_DEV_NVME). When the PCIe bus is enumerated, the NVMe driver recognizes the storage controller and presents the drive to the user space as a standard block device (e.g., /dev/nvme0n1).

Booting from NVMe via SPI Flash

While reading and writing to an NVMe drive is handled by the operating system, booting directly from an NVMe SSD requires firmware support. Because the RK3399 SoC boot ROM cannot read NVMe protocols natively on power-up, developer boards use onboard SPI NOR flash memory.

During the boot process:

  1. The SoC's internal ROM loads the secondary program loader (SPL) and U-Boot from the onboard SPI flash.
  2. U-Boot initializes the PCIe controller and executes the NVMe driver layer.
  3. U-Boot locates the boot partition on the NVMe drive, loads the Linux kernel, device tree blob, and initial RAM disk (initramfs) into system RAM, and transfers execution to the OS.

This multi-stage architecture provides a complete, high-performance NVMe storage implementation that bypasses the speed and endurance limits of traditional microSD and eMMC media.

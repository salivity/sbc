How Distributed SBCs Communicate via MQTT in IIoT

In an Industrial Internet of Things (IIoT) architecture, distributed Single Board Computers (SBCs) act as intelligent edge nodes that gather, process, and exchange telemetry data with central systems or other devices. By leveraging the MQTT (Message Queuing Telemetry Transport) protocol, these SBCs communicate efficiently through a central broker using a lightweight publish-subscribe messaging pattern. This setup optimizes bandwidth, ensures reliable message delivery in challenging industrial environments, and enables scalable, decoupled device communication.

The Role of Single Board Computers (SBCs) at the Edge

SBCs, such as Raspberry Pi, BeagleBone, or industrial-grade equivalents, are deployed close to machinery, sensors, and actuators. Their primary responsibilities include:

  • Data Acquisition: Interfacing directly with sensors and legacy industrial hardware via protocols like Modbus, OPC UA, CAN bus, or GPIO.
  • Edge Computing: Filtering, aggregating, or running analytics on raw data locally to minimize network payload.
  • MQTT Client Operation: Translating processed edge data into standardized MQTT payloads and managing connections to the broker.

The MQTT Publish-Subscribe Model

MQTT relies on an event-driven architecture centered around an MQTT broker (such as Eclipse Mosquitto, EMQX, or HiveMQ). SBCs do not establish direct peer-to-peer links with each other; instead, they operate as clients communicating through the broker.

  1. Publishers: An SBC reads local sensor metrics, packages the data (typically in JSON, Protocol Buffers, or Sparkplug B format), and publishes the message to a specific topic on the broker.
  2. Subscribers: Other SBCs, Human-Machine Interfaces (HMIs), or cloud platforms subscribe to specific topics to receive real-time updates or control instructions.
  3. Broker Routing: The broker receives published messages and filters, manages, and forwards them instantly to all clients subscribed to the relevant topics.

Topic Hierarchies for IIoT Scalability

Communication is organized using hierarchical topic structures separated by forward slashes. This enables granular access control and efficient routing. A standard IIoT topic structure might look like:

enterprise/facility_location/production_line/sbc_id/sensor_type

  • Publishing Telemetry: An SBC on Line 2 might publish to factory_a/line_2/sbc_04/vibration.
  • Receiving Commands: The same SBC can subscribe to factory_a/line_2/sbc_04/commands/# to listen for remote operational parameters or firmware triggers.
  • Wildcard Subscriptions: Central monitoring dashboards can subscribe to factory_a/+/+/vibration to aggregate vibration data from all SBCs across the plant simultaneously.

Ensuring Reliability in Industrial Environments

Industrial networks frequently face intermittent connectivity and harsh electrical interference. MQTT addresses these challenges through built-in mechanisms configured on the SBC clients:

  • Quality of Service (QoS) Levels:
    • QoS 0 (At most once): Minimal overhead, best-effort delivery without confirmation.
    • QoS 1 (At least once): Ensures delivery with acknowledgment; suitable for critical operational alerts.
    • QoS 2 (Exactly once): Highest guarantee with a four-step handshake, preventing duplicate data for critical transaction or state changes.
  • Persistent Sessions and Retained Messages: The broker stores messages for offline SBCs and delivers the latest known good value immediately when a disconnected SBC reconnects.
  • Last Will and Testament (LWT): An SBC registers an LWT message upon connection. If the device unexpectedly disconnects or loses power, the broker automatically publishes an alert to a status topic (e.g., factory_a/sbc_04/status -> OFFLINE), alerting operators to node failure.
  • Keep-Alive Signals: SBCs send periodic heartbeat pings to the broker to maintain open TCP connections and proactively detect network drops.

Security Implementation

To safeguard industrial networks, communication between SBCs and the MQTT broker is secured through:

  • Transport Layer Security (TLS/SSL): Encrypting all data in transit to prevent eavesdropping and man-in-the-middle attacks.
  • Mutual Authentication (mTLS): Requiring X.509 client certificates on each SBC to verify device identity before granting broker access.
  • Access Control Lists (ACLs): Restricting each SBC's permissions so it can only publish and subscribe to its authorized topic namespaces.

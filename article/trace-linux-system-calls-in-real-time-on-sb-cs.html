Trace Linux System Calls in Real Time on SBCs

Tracing Linux kernel system calls in real time on embedded single-board computers (SBCs) is essential for diagnosing software bugs, analyzing performance bottlenecks, and auditing system behavior. Because embedded systems often feature constrained CPU architectures, limited RAM, and flash-based storage, selecting the right tracing utility requires balancing observability against execution overhead. This guide outlines the primary tools used by developers to capture and analyze system calls live on embedded Linux devices.

1. strace

strace is the traditional user-space utility for intercepting and recording system calls made by a process.

  • Mechanism: Relies on the ptrace kernel subsystem to halt execution at every system call entry and exit.
  • Advantages: Pre-installed or easily available in almost all embedded Linux distributions; requires no special kernel compilation options or modules.
  • Limitations: Introduces significant runtime overhead. It can drastically slow down target processes, making it less suitable for high-throughput or time-critical embedded applications.
  • Best Use Case: Quick, ad-hoc debugging of user-space processes where performance degradation is acceptable.

2. ftrace and trace-cmd

ftrace is the official internal tracer of the Linux kernel, built directly into the kernel source tree.

  • Mechanism: Uses the kernel's sys_enter and sys_exit tracepoints within the tracefs virtual filesystem (typically mounted at /sys/kernel/tracing).
  • Advantages: Extremely low overhead compared to ptrace-based tools. The front-end tool trace-cmd allows users to capture, filter, and stream live events over the network to a host PC for analysis.
  • Limitations: Requires CONFIG_FTRACE and CONFIG_HAVE_SYSCALL_TRACEPOINTS enabled in the Linux kernel configuration.
  • Best Use Case: Real-time syscall inspection on resource-constrained devices without impacting the system's timing characteristics.

3. eBPF and bpftrace

Extended Berkeley Packet Filter (eBPF) allows developers to run sandboxed programs inside the Linux kernel without changing kernel source code or loading kernel modules.

  • Mechanism: Attaches tiny, verified bytecode programs to raw syscall tracepoints (raw_syscalls:sys_enter and raw_syscalls:sys_exit) and aggregates data in kernel space.
  • Advantages: Extremely efficient; allows on-the-fly filtering and aggregation, which reduces the volume of data that needs to be sent to user space. High-level front-ends like bpftrace provide single-line command tracing capabilities.
  • Limitations: Requires modern Linux kernels (typically 4.x+ for basic support, 5.x+ for full functionality) with CONFIG_BPF_SYSCALL and BTF (BPF Type Format) enabled, which may not be present in legacy embedded board support packages (BSPs).
  • Best Use Case: Advanced, programmable real-time system call monitoring and latency measurement on modern SBCs (e.g., Raspberry Pi 4/5, newer ARM64 boards).

4. LTTng (Linux Trace Toolkit: Next Generation)

LTTng is a high-performance tracing framework designed for production-grade Linux systems.

  • Mechanism: Uses dedicated kernel modules and user-space libraries to write trace data into lockless ring buffers.
  • Advantages: Produces minimal CPU overhead and deterministic latency, making it safe for hard real-time and production environments. It supports simultaneous tracing of both user-space code and kernel system calls.
  • Limitations: Requires out-of-tree kernel modules or specific patching during the BSP build process (e.g., via Yocto or Buildroot).
  • Best Use Case: Industrial embedded systems, real-time control applications, and long-duration live trace captures.

5. perf

perf is the standard Linux profiling tool that integrates with the kernel's Performance Counters subsystem.

  • Mechanism: Uses the perf_event_open system call to hook into kernel tracepoints and hardware counters.
  • Advantages: Included directly in the Linux kernel source repository. The perf trace subcommand operates similarly to strace but with significantly lower overhead.
  • Limitations: Requires access to debug symbols for full readability and depends on kernel configuration support (CONFIG_PERF_EVENTS).
  • Best Use Case: Profiling system call execution times and identifying which system calls consume the most CPU cycles.

Tuning Linux Scheduler for Real-Time SBC Performance

This article provides a practical guide on tuning the Linux scheduler and associated kernel parameters to achieve deterministic, low-latency performance on Single Board Computers (SBCs). You will learn how to configure real-time scheduling policies, adjust kernel runtime throttles, isolate CPU cores, balance interrupt handling, and optimize thread priorities to prevent latency spikes in embedded environments.

1. Implement Real-Time Scheduling Policies

Standard Linux utilizes the Completely Fair Scheduler (CFS/EEVDF), which prioritizes throughput and fairness over determinism. For deterministic behavior, assign real-time scheduling policies to critical tasks:

  • SCHED_FIFO (First-In, First-Out): Runs a thread until it yields, blocks on I/O, or is preempted by a higher-priority real-time thread.
  • SCHED_RR (Round Robin): Similar to SCHED_FIFO, but assigns time slices to threads of the same priority to share CPU time.
  • SCHED_DEADLINE: Allocates CPU capacity using an Earliest Deadline First (EDF) algorithm based on runtime, period, and deadline parameters.

To set a real-time policy via the command line, use the chrt utility:

# Run a process with SCHED_FIFO and a priority of 80
chrt -f 80 /path/to/application

# Modify an existing process by PID
chrt -f -p 80 <PID>

In C/C++ source code, apply policies using the POSIX thread library:

struct sched_param param;
param.sched_priority = 80;
pthread_setschedparam(pthread_self(), SCHED_FIFO, &param);

2. Configure Real-Time Throttling Parameters

By default, the Linux kernel reserves 5% of CPU time for non-real-time tasks to prevent runaway real-time threads from locking the system. In dedicated SBC systems, this throttling can introduce unexpected jitter.

Scheduler runtime behavior is controlled through sysctl:

  • kernel.sched_rt_period_us: The scheduling period (default is 1000000 µs or 1 second).
  • kernel.sched_rt_runtime_us: The amount of time real-time tasks are allowed to run within that period (default is 950000 µs).

To allow real-time tasks 100% of the CPU runtime without throttling:

# Temporarily disable RT throttling
sudo sysctl -w kernel.sched_rt_runtime_us=-1

# Persist across reboots in /etc/sysctl.conf
echo "kernel.sched_rt_runtime_us = -1" | sudo tee -a /etc/sysctl.conf

Note: Ensure real-time tasks properly sleep or yield, as a busy loop with throttling disabled will freeze the board.

3. CPU Core Isolation and Affinity

SBCs often have limited CPU cores (typically 4 to 8). Isolating dedicated cores for critical tasks prevents the kernel scheduler from placing background processes or worker threads on those cores.

Add the following boot parameters to the bootloader configuration (e.g., cmdline.txt on Raspberry Pi or extlinux.conf/U-Boot environment):

  • isolcpus=2,3: Removes cores 2 and 3 from the general scheduler domain.
  • nohz_full=2,3: Reduces scheduler tick interrupts on isolated cores when a single task runs.
  • rcu_nocbs=2,3: Offloads Read-Copy-Update (RCU) callbacks from isolated cores to housekeeping cores.

Example boot entry:

isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3

Bind real-time applications directly to isolated cores using taskset:

# Pin process to CPU Core 2
taskset -c 2 chrt -f 80 /path/to/application

4. Interrupt (IRQ) Affinity and Threading

Hardware interrupts can disrupt real-time task execution. Route interrupts to non-isolated cores to maintain low latency on real-time cores.

  1. Disable automatic IRQ balancing:

    sudo systemctl stop irqbalance
sudo systemctl disable irqbalance

  2. Manually assign IRQ affinity: Redirect interrupts to non-isolated cores (e.g., Core 0 and Core 1) by writing a bitmask to /proc/irq/<IRQ_NUMBER>/smp_affinity.

    # Direct IRQ 45 to CPU 0 (bitmask 0x1)
echo 1 | sudo tee /proc/irq/45/smp_affinity

  3. Adjust Threaded IRQ Priorities: Under a PREEMPT_RT kernel, hardware interrupts are managed as kernel threads (irq/XX-name). Adjust their priority relative to your application using chrt to prevent less critical hardware events from preempting time-sensitive loops.

5. Memory Locking to Prevent Paging Latency

Scheduler determinism is compromised if a thread is delayed by a page fault. Real-time applications must lock their address space into RAM to prevent memory pages from being paged out or dynamically allocated during execution.

Implement memory locking within the application initialization:

#include <sys/mman.h>

void lock_memory(void) {
    if (mlockall(MCL_CURRENT | MCL_FUTURE) == -1) {
        perror("mlockall failed");
    }
}

Set system resource limits in /etc/security/limits.conf to allow non-root users to lock memory and raise real-time priorities:

* soft rtprio 99
* hard rtprio 99
* soft memlock unlimited
* hard memlock unlimited

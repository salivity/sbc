How to Debug a Custom SBC Using JTAG

Debugging a custom Single Board Computer (SBC) through a JTAG interface requires a systematic approach that isolates issues across hardware, signal integrity, and software configurations. When bringing up a new board, communication failures between the JTAG probe and the target processor are common. This guide outlines the essential troubleshooting steps to diagnose connection faults, detect scan chain errors, and establish a reliable debugging session on custom hardware.

1. Verify Power Rails and Grounding

Before probing data lines, ensure the target board is powered correctly.

  • Target Reference Voltage (\(V_{REF}\) / \(V_{TARGET}\)): Verify that the JTAG probe detects the correct I/O voltage (e.g., 3.3V, 1.8V) from the target board. If this pin is floating or unpowered, the debugger’s level shifters will not function.
  • Common Ground: Confirm a solid ground connection between the JTAG adapter and the custom SBC to prevent ground loop offsets and floating logic levels.
  • Core and I/O Rails: Ensure all System-on-Chip (SoC) or Microcontroller (MCU) power rails are stable and within operational tolerances using a digital multimeter or oscilloscope.

2. Check JTAG Pinout and Physical Connections

Wiring mistakes are the most frequent cause of failure on custom revisions.

  • Pin Mapping: Double-check the schematic and PCB layout against the debug probe’s standard pinout (e.g., ARM 10-pin, ARM 20-pin, or standard MIPS/RISC-V headers). Common errors include swapped TDI/TDO lines or mirrored pin numbering.
  • Pull-Up and Pull-Down Resistors: Verify that standard pull-up or pull-down termination resistors are installed according to the target processor’s hardware design guide (typically on TMS, TDI, and TCK).
  • Cable Length: Keep ribbon cables short (under 15–20 cm) to minimize parasitic capacitance and cross-talk.

3. Lower the JTAG Clock Frequency (TCK)

High-speed clocking can fail on prototype boards with unoptimized trace routing.

  • Lower the JTAG adapter clock speed (TCK) in your debugging software (such as OpenOCD, J-Link Commander, or GDB) to a conservative value, such as 100 kHz or 500 kHz.
  • If communication succeeds at lower frequencies, the issue is related to trace capacitance, poor termination, or excessive line length.

4. Analyze Signal Integrity with an Oscilloscope

If the probe still fails to detect the target, inspect the physical waveforms.

  • Inspect TCK, TMS, and TDI: Probe these lines close to the SoC pins to check for clean square waves, ringing, slow rise times, or excessive overshoot.
  • Observe TDO: The Target Data Out (TDO) pin should toggle in response to scan chain commands. If TDO remains continuously high, low, or floating, the Test Access Port (TAP) controller inside the SoC is not processing commands.

5. Validate Reset Signals and Boot Modes

Reset states and boot configurations can prevent the debug unit from taking control of the core.

  • nSRST and nTRST Lines: Verify whether your target uses System Reset (nSRST), Test Reset (nTRST), or both. Ensure the debugger is not holding the SoC in permanent reset.
  • Boot Strapping Pins: Ensure the processor’s hardware bootstrap pins are configured correctly. Some SoCs disable JTAG functionality in certain secure boot modes or enter low-power sleep states immediately after power-up, severing the JTAG link.
  • Under-Reset Halting: Configure the debugger to halt the processor immediately out of reset (reset halt or connect under reset) to prevent faulty firmware from crashing the CPU or reconfiguring JTAG pins as standard GPIOs.

6. Test the Scan Chain and IDCODE Extraction

Once basic signaling works, use your debug utility to query the JTAG Test Access Port (TAP).

  • Run a basic scan chain autodetection command (e.g., scan_chain in OpenOCD).
  • Verify that the returned Device ID (IDCODE) matches the silicon manufacturer's datasheet.
  • A readback value of 0x00000000 or 0xFFFFFFFF indicates a physical line fault (such as a disconnected or shorted TDO line).

7. Confirm Debugger Configuration Files

Software misconfigurations can cause initial attachment failures even when hardware is intact.

  • Ensure your OpenOCD, PyOCD, or proprietary debugger scripts reference the exact SoC variant, core type (e.g., Cortex-M4, Cortex-A53), and memory map.
  • Verify that the debug software is configured for JTAG mode rather than Serial Wire Debug (SWD) or cJTAG, unless your hardware specifically uses those alternative protocols.

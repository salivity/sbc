Debugging Kernel Panics via Serial on SBCs

This guide provides a practical walkthrough for embedded engineers to capture and analyze Linux kernel panic events on Single Board Computers (SBCs) using a hardware serial console. When a kernel panics, graphical displays and network interfaces often freeze instantly, making low-level UART serial communication the most reliable way to extract stack traces, identify faulty drivers, and locate memory faults.

1. Hardware Connection Setup

To capture early boot and panic messages, establish a physical UART connection between the host development machine and the SBC.

  • Required Hardware: A 3.3V USB-to-UART bridge (such as FTDI FT232R, CP2102, or CH340).
  • Pin Connections:
    • GND on the adapter to GND on the SBC.
    • RX on the adapter to TX on the SBC UART header.
    • TX on the adapter to RX on the SBC UART header (optional, but required for interactive SysRq commands).
    • Do not connect the VCC/power pins between the USB-UART adapter and the SBC.

2. Configure the Kernel Command Line (bootargs)

The bootloader (such as U-Boot) must instruct the Linux kernel to route all log messages to the serial port, including early boot routines. Update your device's bootargs or extlinux.conf:

console=ttyS0,115200n8 earlycon=uart8250,mmio32,0x01c28000 ignore_loglevel loglevel=8 panic=0
  • console=ttyS0,115200n8: Sets the primary console port and baud rate (adjust ttyS0 or ttyAMA0 based on your SoC).
  • earlycon: Enables early printk output before the full serial driver initializes.
  • ignore_loglevel: Forces the kernel to output all messages, including debugging data, directly to the console.
  • panic=0: Prevents the board from automatically rebooting immediately after a panic, preserving terminal output.

3. Log the Serial Session on the Host

Open a terminal emulator on your host PC that automatically writes all received data to a persistent log file:

Using picocom:

picocom -b 115200 /dev/ttyUSB0 --logfile kernel_panic.log

Using minicom:

minicom -D /dev/ttyUSB0 -b 115200 -C kernel_panic.log

Using screen:

screen -L -Logfile kernel_panic.log /dev/ttyUSB0 115200

4. Anatomy of a Kernel Panic Log

When a panic occurs, examine the generated log file for several key components:

  1. The Panic Banner: Indicates the immediate reason for failure (e.g., Kernel panic - not syncing: Fatal exception in interrupt, Unable to handle kernel NULL pointer dereference).
  2. CPU Registers: Shows the Program Counter (PC on ARM, RIP on x86) and Link Register (LR), pointing to the exact instruction that triggered the fault.
  3. Call Trace: Displays the reverse execution path leading to the crash. Read the trace from bottom to top to identify which function invoked the failing code.
  4. Tainted State: A line starting with CPU: X PID: Y Comm: ... Tainted: indicates whether third-party or proprietary drivers were loaded, which may have caused instability.

5. Decoding Addresses to Source Code

The raw panic output lists hex offsets rather than exact lines of code (e.g., my_driver_probe+0x48/0x120). Map these offsets back to your source code using cross-compilation tools and an unstripped kernel image (vmlinux).

Using addr2line

Locate the offending instruction address:

aarch64-linux-gnu-addr2line -e vmlinux -f -p 0xffffff8008082148

This command outputs the source file and line number responsible for the panic.

Using GDB

Load the unstripped kernel binary in GDB:

gdb-multiarch vmlinux
(gdb) list *(my_driver_probe+0x48)

GDB will print the source code context directly surrounding the failing instruction.

6. Triggering Manual Panics for Testing

If testing a serial logging pipeline or watchdog response, manually trigger a panic over the serial console using Magic SysRq keys:

echo 1 > /proc/sys/kernel/sysrq
echo c > /proc/sysrq-trigger

If the system shell is unresponsive, send a serial BREAK signal through your terminal client (e.g., Ctrl+A then Ctrl+B in minicom) followed by the c key to initiate an immediate crash dump over the UART line.

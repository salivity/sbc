Custom GPIO Pinmux Configuration in SBC Bootloader

Configuring custom GPIO pin multiplexing (pinmux) in a Single Board Computer (SBC) bootloader ensures that peripheral interfaces, power rails, and status lines are established before the main operating system kernel boots. This process involves identifying target pin registers via SoC datasheets, updating bootloader source files—typically within Das U-Boot via Device Tree Source (DTS) nodes or platform-specific C code—compiling the modified bootloader image, flashing it to non-volatile storage, and validating the pin states on the physical hardware.

Step 1: Identify Hardware Registers and Mux Functions

Before altering software, consult the SBC schematic and the SoC reference manual:

  1. Find Pin Names: Locate the specific header or ball grid array (BGA) pin name in the SBC schematic.
  2. Determine Multiplexing Options: Look up the pin in the SoC reference manual to identify its register offset and the required multiplexing mode (e.g., ALT0, ALT1, GPIO mode, I2C, SPI, or UART).
  3. Determine Electrical Characteristics: Identify needed internal pull-up/pull-down resistors, drive strength, slew rate, and Schmitt trigger settings.

Step 2: Locate the Configuration Mechanism in the Bootloader

Most modern SBC bootloaders (such as U-Boot) configure pinmux settings using one of two methods:

  • Device Tree (FDT/OF_CONTROL): Standard in modern U-Boot builds. Configurations reside in .dts and .dtsi files within the arch/<arch>/dts/ directory.
  • Direct Register Initialization (C Source): Common in low-level Secondary Program Loaders (SPL) or legacy implementations. Configurations reside in board/<vendor>/<board_name>/ or arch/<arch>/mach-<soc>/.

Step 3: Implement the Pinmux Configuration

Method A: Modifying the Device Tree (Recommended)

  1. Open the board's DTS or DTSI file in the bootloader source tree (e.g., arch/arm/dts/<board-name>.dts).
  2. Locate or define a pinctrl node corresponding to your pin controller.
  3. Define a custom pinmux group:
&pinctrl {
    pinctrl_custom_gpios: custom-gpios-grp {
        fsl,pins = <
            /* Pin Definition Macro, Config Value (Pull-up, drive strength, mux mode) */
            MX8MQ_IOMUXC_SAI5_RXD1_GPIO3_IO22    0x19
            MX8MQ_IOMUXC_SAI5_RXD2_GPIO3_IO23    0x19
        >;
    };
};
  1. Assign the pin group to the target peripheral node, or configure them early as static GPIOs using a gpio-hog or an always-active device node:
&gpio3 {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_custom_gpios>;
    status = "okay";
};

Method B: Modifying Board C Code (Board Init Level)

If the target architecture sets up pad configurations via C structures (e.g., NXP i.MX platforms with IOMUX macros or Rockchip platform files):

  1. Open the board initialization file (e.g., board/<vendor>/<board_name>/<board_name>.c).
  2. Add the pin definitions to the pad configuration array:
static iomux_v3_cfg_t const custom_pads[] = {
    IOMUX_PADS(PAD_CTL_PUS_100K_UP | PAD_CTL_PUE | PAD_CTL_SPEED_MED),
    IMX8MQ_PAD_SAI5_RXD1__GPIO3_IO22 | MUX_PAD_CTRL(NO_PAD_CTRL),
};
  1. Call the pad configuration routine inside an early boot function, such as board_early_init_f() or board_init():
imx_iomux_v3_setup_multiple_pads(custom_pads, ARRAY_SIZE(custom_pads));

Step 4: Recompile the Bootloader

  1. Set up the target cross-compilation toolchain: 
    export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-
  2. Load the board's default configuration: 
    make <board_defconfig>
  3. Build the binary images: 
    make -j$(nproc)

The compilation generates updated boot artifacts, such as u-boot.bin, u-boot-with-spl.bin, or u-boot.itb.

Step 5: Flash the New Bootloader Image

Flash the compiled bootloader to the designated boot medium (SD card, eMMC, or SPI NOR flash) using the appropriate offset specified by the SoC vendor:

sudo dd if=u-boot-with-spl.bin of=/dev/sdX bs=1k seek=33 status=progress conv=fsync

Step 6: Verify Pin States at Runtime

  1. U-Boot Interactive Shell: Interrupt the boot sequence via serial UART to access the U-Boot command prompt.
  2. Inspect GPIOs: Run GPIO management commands to verify direction and state: 
    => gpio status -a
=> gpio input <pin_number>
=> gpio set <pin_number>
  3. Inspect Raw Registers: Use memory display commands to confirm the pinmux control register matches the expected bitmask: 
    => md.l <pin_register_physical_address> 1
  4. Physical Verification: Use a multimeter or oscilloscope on the target SBC header pins to confirm voltage levels, drive logic, and signal behavior.

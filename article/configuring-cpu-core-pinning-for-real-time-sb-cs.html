Configuring CPU Core Pinning for Real-Time SBCs

CPU core pinning, or processor affinity, is a critical optimization technique used on multi-core real-time Single Board Computers (SBCs) to achieve deterministic execution. By dedicating specific CPU cores exclusively to time-critical tasks and offloading system overhead, background services, and non-critical interrupts to other cores, engineers can eliminate jitter and unpredictable context switching. This guide outlines the essential steps required to isolate cores, redirect system interrupts, and programmatically bind real-time processes on an embedded Linux SBC.

1. Isolate Cores at the Kernel Level

The first step in core pinning is preventing the Linux kernel scheduler from assigning standard user-space processes to the target real-time cores. This is achieved by passing isolation parameters via the SBC bootloader (such as U-Boot or platform-specific configuration files like cmdline.txt or armbianEnv.txt).

Add the following kernel boot parameters:

  • isolcpus=2,3: Removes CPU cores 2 and 3 from the general scheduling pool.
  • nohz_full=2,3: Reduces or eliminates timer ticks on the isolated cores when only one runnable task is present, preventing periodic scheduling interruptions.
  • rcu_nocbs=2,3: Offloads Read-Copy-Update (RCU) callback processing from the isolated cores to non-isolated cores.

2. Redirect Hardware and Software Interrupts

By default, hardware interrupts (IRQs) can disrupt execution on any core. To maintain real-time determinism, IRQs must be steered away from the isolated cores.

  • Disable or Configure irqbalance: Stop the automatic IRQ balancing daemon, or configure /etc/default/irqbalance to exclude real-time cores using the IRQBALANCE_BANNED_CPUS bitmask.
  • Set Affinity Masks Manually: Assign specific IRQs to non-isolated cores via sysfs. For example, writing a hexadecimal CPU mask to /proc/irq/<IRQ_NUMBER>/smp_affinity ensures that peripheral interrupts (such as Ethernet, Wi-Fi, or USB) execute only on housekeeping cores (e.g., Core 0 and Core 1).

3. Bind Applications Programmatically

Once the hardware and kernel are configured, real-time applications must explicitly attach themselves to the isolated cores using POSIX system calls.

In C or C++, use sched_setaffinity() or pthread_setaffinity_np():

#define _GNU_SOURCE
#include <pthread.h>
#include <sched.h>

void pin_thread_to_core(int core_id) {
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(core_id, &cpuset);

    pthread_t current_thread = pthread_self();
    pthread_setaffinity_np(current_thread, sizeof(cpu_set_t), &cpuset);
}

Combine core pinning with real-time scheduling policies (SCHED_FIFO or SCHED_DEADLINE) using sched_setscheduler() to guarantee task priority over any kernel threads that may remain.

4. Assign Cores via Runtime Utilities

For pre-compiled binaries or quick validation, utilities such as taskset and chrt allow manual binding from the command line:

# Run a real-time binary pinned to Core 2 with FIFO priority 80
chrt -f 80 taskset -c 2 ./realtime_app

5. Mitigate Memory and Cache Latency

Core pinning must be paired with memory management to avoid non-deterministic execution spikes:

  • Lock Memory: Use mlockall(MCL_CURRENT | MCL_FUTURE) to keep process memory in RAM, preventing page faults.
  • Cache Partitioning: On SBC architectures that support it (such as ARM Cache Stashing or Intel RDT), reserve dedicated L2/L3 cache slices for the pinned cores to prevent shared cache eviction caused by non-real-time processes.

Using Hardware Watchdog Timers on Single Board Computers

Hardware watchdog timers (WDTs) are critical components used by embedded developers to ensure that single board computers (SBCs) recover automatically from software crashes, deadlocks, and system freezes. This article explores how developers configure and utilize hardware watchdogs on SBCs, covering the initialization process, "petting" mechanisms, software architecture integration, and best practices for creating resilient autonomous systems.

Understanding the Hardware Watchdog

A hardware watchdog timer is an independent timing circuit integrated into the SBC’s System on Chip (SoC) or mounted as an external dedicated integrated circuit. It operates on a simple countdown principle: the timer continuously counts down from a predefined threshold. If the timer reaches zero, it triggers a hardware reset line, power-cycling or rebooting the SBC. To prevent this reboot, the running software must periodically reset—or "kick"—the timer before it expires.

Enabling and Configuring the Watchdog

On Linux-based SBCs (such as Raspberry Pi, BeagleBone, or industrial i.MX-based boards), developers access the hardware watchdog through kernel drivers exposed via the /dev/watchdog device node.

  1. Kernel and Device Tree Setup: Developers enable the appropriate SoC watchdog driver in the Linux kernel configuration (e.g., CONFIG_BCM2835_WDT or CONFIG_IMX2_WDT) and ensure the hardware interface is defined in the Device Tree.
  2. Setting Timeouts: Using standard Linux ioctl calls or configuration files, developers define the watchdog timeout interval (typically ranging from a few seconds to a couple of minutes), giving the operating system enough margin to operate under heavy load without triggering false resets.

Implementing the "Petting" Strategy

Embedded engineers use different levels of watchdog management depending on the reliability requirements of the system:

  • System-Level Monitoring (systemd / watchdogd): Linux services such as systemd natively support watchdog hardware. By enabling RuntimeWatchdogSec= in systemctl.conf, the init system regularly pings /dev/watchdog. If the kernel hangs or core operating system services lock up, systemd stops kicking the timer, forcing a hardware reboot.
  • Application-Level Heartbeats: For mission-critical applications, relying solely on system-level daemons is insufficient because a critical process can crash while the background OS remains healthy. Developers implement application heartbeats where primary tasks, sensor-polling loops, and communication threads must all report health to a central supervisor process before that supervisor pings the watchdog.

Advanced Architectural Techniques

To build robust embedded designs, developers adopt several advanced watchdog patterns:

  • Staged Watchdogs (Windowed Watchdogs): Some hardware WDTs require kicks to occur within a specific time window—neither too late nor too early. This detects situations where code executes in an uncontrolled tight loop.
  • Safe-State Bootstrapping: Upon receiving a watchdog-induced reset, bootloader code (such as U-Boot) detects the reset source register. If repeated resets occur, the bootloader can roll back a faulty firmware update, boot into a recovery partition, or signal an alert.
  • Graceful Shutdown Hooks: Before the final reset triggers, certain watchdogs generate a Non-Maskable Interrupt (NMI) shortly before the hardware reset. Developers utilize this brief window to flush critical data to non-volatile storage or write debugging registers for post-mortem analysis.

CI/CD Pipelines for Custom SBC Image Builds

Building and testing operating system images for custom single board computers (SBCs) requires a continuous integration (CI) pipeline that automates Board Support Package (BSP) compilation, root filesystem generation, and validation across both emulated and physical hardware. This article details the structural stages of an embedded CI/CD pipeline—from environment setup and caching strategies to image generation, Hardware-in-the-Loop (HIL) testing, and artifact deployment.

1. Build Environment and Runner Architecture

Embedded Linux image builds are resource-intensive. Developers typically avoid public cloud-hosted shared runners due to CPU, storage, and execution time limits.

  • Dedicated Self-Hosted Runners: Pipelines run on high-core bare-metal servers or self-hosted VMs with 32+ CPU cores, 64 GB+ RAM, and fast NVMe storage.
  • Containerized Build Environments: Build dependencies (toolchains, SDKs, host utilities) are packaged inside Docker containers to guarantee reproducibility across team members and CI agents.
  • Aggressive Caching: Build systems like the Yocto Project (BitBake) or Buildroot rely on persistent storage caches. Runners mount persistent volumes for download directories (DL_DIR) and shared state caches (SSTATE_DIR) to reduce build times from hours to minutes on incremental commits.

2. Source Control and Pipeline Triggers

Custom SBC repositories are generally structured into modular layers: the kernel/U-Boot source, custom hardware layers (meta-layers), and application stacks.

  • Trigger Rules: Full image builds are triggered on release tags or merges to the main branch. Lightweight smoke tests or pull request (PR) builds compile only modified packages or recipes to provide fast feedback.
  • Manifest Management: Tools like repo (Google's multi-git management tool) or Git submodules track explicit commit hashes of external layers to ensure deterministic builds.

3. Image Compilation Stage

Once triggered, the pipeline orchestrates the build system to generate partition tables and bootable binaries:

  • Target Selection: The pipeline defines environment variables specifying the target board (MACHINE), image type (minimal, development, production), and init system (systemd, SysVinit).
  • Artifact Generation: The output includes the bootloader (U-Boot), Linux kernel (zImage/Image), Device Tree Blobs (.dtb), kernel modules, and raw disk images (.wic, .img, .sdcard).
  • Software Bill of Materials (SBOM): The build automatically outputs license manifests and vulnerability reports (e.g., using cve-check in Yocto) to detect unpatched CVEs.

4. Emulation and Virtual Testing

Before touching physical hardware, images pass automated virtual validation to fail fast on critical boot or configuration errors:

  • QEMU Emulation: The CI launches QEMU matching the SBC's processor architecture (ARM, ARM64, or RISC-V) with the generated kernel and rootfs.
  • Smoke Testing: Automated scripts (via Python, Bash, or pytest) verify that the system completes the boot process, mounts filesystems correctly, starts critical systemd services, and responds to network commands.

5. Hardware-in-the-Loop (HIL) Testing

To validate physical peripheral controllers (GPIO, I2C, SPI, CAN) and power management that QEMU cannot simulate, the pipeline integrates physical test benches.

  • Test Frameworks: Frameworks such as LAVA (Linaro Automated Validation Architecture) or Labgrid manage boards connected to the CI infrastructure.
  • Flashing and Power Control: Automated smart power switches (PDUs) power-cycle the board. SD-mux devices or network boot servers (TFTP/NFS) flash the newly built image to the physical SBC's eMMC or SD card.
  • Serial Console Automation: The test runner monitors UART serial outputs using tools like pexpect to confirm the U-Boot sequence, kernel handoff, and userspace login.
  • Peripheral Verification: Automated test suites run on-device commands to check communication across exposed interfaces and loopback circuits.

6. Artifact Signing, Packaging, and Distribution

Once all tests pass, the pipeline packages the verified build artifacts for deployment:

  • Signing: Cryptographic signatures are applied to the kernel, bootloader, and rootfs for Secure Boot verification.
  • OTA Packaging: Dual-copy (A/B) Over-The-Air update payloads (e.g., RAUC, Mender, or SWUpdate bundles) are generated alongside the raw flash images.
  • Storage and Release: The pipeline uploads compressed images and update bundles to an artifact repository (such as JFrog Artifactory, AWS S3, or internal package feeds), indexed by Git commit hash and release tags.

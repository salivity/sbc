How to Configure DMA Channels on Modern SBCs

Direct Memory Access (DMA) allows hardware peripherals to transfer data directly to and from system memory without continuous CPU intervention, drastically reducing processor overhead in embedded systems. On modern Single Board Computers (SBCs) running embedded Linux, configuring DMA channels involves declaring hardware routing in the Device Tree, allocating cache-coherent memory buffers, configuring channel parameters via the Linux DMAEngine subsystem, and handling asynchronous transfer callbacks.

1. Declare DMA Resources in the Device Tree

Modern SBCs use Device Tree Source (.dts) files to describe hardware topology. To link a peripheral (such as an SPI, UART, or I2S controller) to a DMA controller, the peripheral node must specify its DMA channels and request lines.

  • Locate the DMA Controller: Ensure the DMA controller node is enabled and provides a #dma-cells property (defining the number of arguments required to specify a channel or request line).
  • Reference DMA in the Peripheral Node: Use the dmas and dma-names properties to map the transmit (TX) and receive (RX) channels.
&spi1 {
    dmas = <&dma0 14>, <&dma0 15>;
    dma-names = "tx", "rx";
    status = "okay";
};

2. Allocate DMA-Safe Memory Buffers

Standard dynamically allocated memory (via kmalloc or user space) can be swapped, fragmented, and cached, which leads to memory corruption during DMA transfers. Embedded drivers must allocate physically contiguous, DMA-accessible buffers.

  • Coherent Mappings (Consistent DMA): Used for non-time-critical buffers that are shared continuously between the device and CPU. 
    dma_addr_t dma_handle;
void *cpu_addr = dma_alloc_coherent(dev, size, &dma_handle, GFP_KERNEL);
  • Streaming Mappings: Used for one-off transfers (like network packets) where memory is mapped immediately before the transfer and unmapped after, ensuring CPU caches are properly flushed or invalidated. 
    dma_addr_t dma_handle = dma_map_single(dev, buffer, size, DMA_TO_DEVICE);

3. Request and Configure the Channel via DMAEngine

Kernel drivers interact with DMA controllers using the Linux DMAEngine API (linux/dmaengine.h).

  1. Request the Channel: Obtain the channel configured in the Device Tree using dma_request_chan(): 
    struct dma_chan *tx_chan = dma_request_chan(dev, "tx");
if (IS_ERR(tx_chan)) {
    /* Handle channel allocation failure */
}
  2. Set Slave Configuration: Configure data widths, burst sizes, and peripheral register addresses using struct dma_slave_config: 
    struct dma_slave_config config = {
    .direction = DMA_MEM_TO_DEV,
    .dst_addr = peripheral_phys_base_addr,
    .dst_addr_width = DMA_SLAVE_BUSWIDTH_2_BYTES,
    .dst_maxburst = 4,
};
dmaengine_slave_config(tx_chan, &config);

4. Prepare, Submit, and Trigger the Transfer

Once the channel is configured, create a DMA descriptor representing the transfer.

  1. Prepare Descriptor: Generate a descriptor matching your transfer type (single buffer, scatter-gather, or cyclic for audio streaming): 
    struct dma_async_tx_descriptor *desc = dmaengine_prep_slave_single(
    tx_chan, dma_handle, size, DMA_MEM_TO_DEV, DMA_PREP_INTERRUPT | DMA_CTRL_ACK);
  2. Assign Callback: Set a completion callback function and custom context data: 
    desc->callback = dma_transfer_complete_callback;
desc->callback_param = custom_data_ptr;
  3. Submit and Fire: Enqueue the descriptor and trigger the DMA engine hardware: 
    dma_cookie_t cookie = dmaengine_submit(desc);
dma_async_issue_pending(tx_chan);

5. Handle Teardown and Cleanup

When transfers complete or the driver module unloads, clean up allocated resources to prevent memory leaks and hardware locks:

  • In the completion callback or error routines, unmap streaming memory using dma_unmap_single().
  • Stop any ongoing transfers using dmaengine_terminate_sync(tx_chan).
  • Free the DMA channel using dma_release_channel(tx_chan).
  • Free coherent buffers using dma_free_coherent(dev, size, cpu_addr, dma_handle).

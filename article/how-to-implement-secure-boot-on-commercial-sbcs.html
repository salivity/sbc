How to Implement Secure Boot on Commercial SBCs

Implementing hardware-level secure boot on a commercial single board computer (SBC) requires establishing an unbroken chain of trust that starts with on-chip hardware and extends through the operating system kernel. This article outlines the architectural principles and practical steps necessary to configure hardware-level secure boot on standard SBC platforms, covering key generation, eFuse programming, bootloader signing, and final hardware enforcement.

1. Establish the Hardware Root of Trust

Hardware-level secure boot relies on immutable code embedded directly into the System on Chip (SoC), known as the Boot ROM (Primary Bootloader). Because this ROM code is etched during manufacturing, it serves as the initial Root of Trust (RoT). When power is applied, the Boot ROM executes first and verifies the cryptographic signature of the secondary boot stage before allowing execution to proceed.

2. Generate Cryptographic Key Pairs

Before configuring the target hardware, you must establish a secure key management pipeline:

  • Asymmetric Key Pairs: Generate private/public key pairs (typically RSA-2048/4096 or ECC curves like NIST P-256) inside a dedicated Hardware Security Module (HSM) or an isolated build environment.
  • Key Hashing: Generate a cryptographic hash (e.g., SHA-256) of the public key or public key certificate. This hash is what physically resides on the SBC.
  • Symmetric Keys (Optional): If the SoC supports transparent flash encryption, generate AES keys to protect data confidentiality at rest.

3. Program the eFuses / OTP Memory

Commercial SBCs based on platforms like NXP i.MX, Allwinner, Rockchip, or Raspberry Pi utilize One-Time Programmable (OTP) memory or eFuses:

  • Write Public Key Hashes: Burn the hash of your RoT public key into designated eFuse registers. The Boot ROM compares the public key embedded in the signed bootloader binary against this hardware-stored hash.
  • Configure Security Parameters: Set operational fuses that enforce signature checking, define rollback protection parameters, and specify allowed cryptographic algorithms.

Caution: Burning eFuses is an irreversible physical process. Incorrect values or corrupted keys will permanently render the SoC unbootable.

4. Sign and Verify the Boot Chain

Every executable image loaded from external storage (e.g., eMMC, SD card, SPI flash) must be signed using the corresponding private key:

  • First-Stage Bootloader (SPL / FSBL): Signed with the RoT private key; verified by the Boot ROM.
  • Secondary Bootloader (U-Boot / TF-A): Signed and verified by the SPL before handoff.
  • Operating System Kernel and Device Tree: U-Boot utilizes FIT (Flattened Image Tree) image signing to verify the Linux kernel, device tree blob (DTB), and initial ramdisk (initramfs) before execution.

|   Boot ROM    | -> (Hardware Root of Trust)

5. Enforce Lock-Down and Disable Debug Interfaces

Once the boot artifacts are signed and tested in an open/development mode:

  • Burn the Secure Boot Enable Fuse: Blow the specific eFuse that switches the SoC from open mode to strictly enforced secure boot mode. Once blown, the Boot ROM will refuse to boot any unsigned or improperly signed code.
  • Disable Hardware Debugging: Burn configuration fuses that disable JTAG, boundary scan, and unauthorized serial console access to prevent physical memory tampering during runtime.

6. Extend Trust to User Space

Secure boot guarantees the integrity of the kernel, but the integrity of the operating system file system must also be maintained:

  • dm-verity: Configure the Linux kernel to verify the root filesystem block-by-block using a signed hash tree via dm-verity.
  • IMA/EVM: Implement Integrity Measurement Architecture (IMA) and Extended Verification Module (EVM) to prevent runtime modification of system binaries and configuration files.

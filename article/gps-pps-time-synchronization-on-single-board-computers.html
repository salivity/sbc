GPS PPS Time Synchronization on Single Board Computers

Achieving microsecond-level localized time synchronization on a Single Board Computer (SBC) requires combining serial NMEA data with a hardware Pulse Per Second (PPS) signal from a GPS receiver. This guide outlines the end-to-end implementation process, including hardware wiring to GPIO pins, enabling Linux kernel PPS drivers, capturing raw timing data via GPS daemons, and configuring time servers like Chrony to establish a Stratum 1 local time source.

Hardware Interfacing

To begin, connect a GPS module capable of PPS output to the SBC's expansion header:

  1. Power and Ground: Connect the GPS module’s VCC and GND pins to the appropriate 3.3V/5V and Ground pins on the SBC.
  2. UART (Serial Data): Connect the GPS TX pin to the SBC's RX pin (and GPS RX to SBC TX if bidirectional configuration is needed). This interface transmits standard NMEA sentences containing the coarse time (year, month, day, hour, minute, second).
  3. PPS Line: Connect the GPS PPS pin to an interrupt-capable GPIO pin on the SBC. The PPS line sends a sharp electrical pulse precisely at the start of every second, providing sub-microsecond edge accuracy.

Kernel and Device Tree Configuration

The operating system must recognize the GPIO pin as a dedicated PPS source. On Linux-based SBCs (such as Raspberry Pi OS, Armbian, or custom Yocto builds):

  1. Enable the PPS Module: Ensure pps-gpio is compiled into the kernel or loaded as a kernel module (modprobe pps-gpio).
  2. Configure Device Tree: Add an overlay defining the chosen GPIO pin. For example, on a Raspberry Pi, append the following to /boot/config.txt (or /boot/firmware/config.txt): 
    dtoverlay=pps-gpio,gpiopin=18
  3. Reboot and Verify: After rebooting, confirm the PPS device creation: 
    ls /dev/pps*
    Install pps-tools and run ppstest to observe the hardware pulses: 
    sudo ppstest /dev/pps0
    A successful setup outputs timestamps with near-zero jitter every second.

GPS Data Routing with gpsd

While the PPS signal supplies high-precision pulse boundaries, it does not identify which second is occurring. The serial NMEA stream fills this gap.

  1. Install the GPS daemon: 
    sudo apt-get install gpsd gpsd-clients
  2. Configure /etc/default/gpsd to listen to both the serial UART device and the PPS device: 
    DEVICES="/dev/ttyAMA0 /dev/pps0"
GPSD_OPTIONS="-n"
USBAUTO="false"
  3. Restart the service and test using cgps or gpsmon to ensure satellite lock and accurate coordinate/time acquisition.

Configuring the NTP Daemon (Chrony)

Chrony is the preferred time daemon for embedded Linux due to its fast synchronization and handling of unstable clocks.

  1. Install Chrony:

    sudo apt-get install chrony

  2. Edit /etc/chrony/chrony.conf to consume both the NMEA time (via gpsd shared memory or socket) and the direct kernel PPS device:

    # Coarse time from GPS via SHM (refclock 0)
refclock SHM 0 refid GPS precision 1e-1 offset 0.128 delay 0.2 noselect

# Fine time from PPS (Kernel PPS API)
refclock PPS /dev/pps0 refid PPS precision 1e-7 lock GPS prefer

    Note: The noselect directive on the NMEA source tells Chrony to use Nrony to determine the second count, while lock GPS prefer forces Chrony to lock its phase precisely to the PPS edge.

  3. If operating as a local NTP server for other network devices, allow local subnets:

    allow 192.168.1.0/24

Verification and Monitoring

Restart Chrony (sudo systemctl restart chrony) and verify the synchronization status:

chronyc sources -v

Look for the PPS refclock entry. A #* indicator next to PPS confirms that the SBC is actively disciplined by the hardware pulse, with offset and jitter metrics typically falling within the sub-microsecond to low-microsecond range.

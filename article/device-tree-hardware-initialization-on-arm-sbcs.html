Device Tree Hardware Initialization on ARM SBCs

This article provides an overview of how Device Tree configuration is utilized in ARM single board computers (SBCs) to discover, configure, and initialize non-discoverable peripheral hardware. It covers the fundamental role of the Device Tree, the structure of hardware description nodes, the matching process between the Linux kernel and device drivers, and how Device Tree overlays enable modular hardware expansion.

The Role of the Device Tree in ARM Architecture

Unlike traditional x86 computer architectures that rely on discoverable buses (such as PCI/PCIe) or standard ACPI tables to identify connected hardware, ARM-based systems typically integrate peripherals directly via non-discoverable memory-mapped registers, GPIO pins, and serial buses (I2C, SPI, UART).

Because the Linux kernel cannot automatically detect these components at runtime, it relies on a Device Tree (DT). The Device Tree is a structured, hierarchical database that describes the exact physical hardware layout of the board to the operating system, decoupling the kernel binary from board-specific hardware implementations.

Device Tree Components and Workflow

The lifecycle of a Device Tree involves three primary formats:

  1. Device Tree Source (.dts / .dtsi): Human-readable text files written by board vendors or developers. .dtsi files contain shared SoC-level definitions (like CPU cores and built-in controllers), while .dts files define board-specific connections and peripherals.
  2. Device Tree Compiler (dtc): A utility that compiles .dts files into a binary format.
  3. Device Tree Blob (.dtb): The compiled, machine-readable binary file read by the bootloader and the operating system kernel during startup.

Anatomy of a Peripheral Node

A peripheral in a Device Tree is represented as a node with specific properties describing its connectivity and resource allocation:

&i2c1 {
    status = "okay";

    temperature_sensor: sensor@48 {
        compatible = "ti,tmp102";
        reg = <0x48>;
        interrupt-parent = <&gpio1>;
        interrupts = <16 2>; /* GPIO 16, falling-edge trigger */
    };
};

Key properties used for peripheral initialization include:

  • compatible: A string (or list of strings) that links the hardware node to its corresponding device driver in the kernel (e.g., "ti,tmp102").
  • reg: The base memory address and range for memory-mapped peripherals, or the bus address (such as 0x48 for an I2C client).
  • interrupts / interrupt-parent: Specifies the interrupt line and trigger type for peripheral signaling.
  • clocks and clock-names: References to clock controllers providing timing signals to the hardware.
  • pinctrl-*: Pin multiplexing settings required to route signals to the correct physical pins.
  • status: Indicates whether the device is operational ("okay") or disabled ("disabled").

The Initialization Process in the Linux Kernel

When an ARM SBC boots, the bootloader (such as U-Boot) loads both the kernel image and the .dtb file into RAM, passing the memory address of the Device Tree to the kernel.

The kernel then initializes hardware through the following sequence:

  1. Unflattening the Tree: The kernel converts the binary .dtb into an in-memory tree of device_node structures.
  2. Platform Device Creation: The kernel traverses the tree and creates a struct platform_device (or subsystem-specific device, such as i2c_client or spi_device) for each active peripheral node.
  3. Driver Matching: The kernel's driver core iterates through registered drivers and compares their of_match_table against the compatible strings in the Device Tree nodes.
  4. Driver Probing: Once a match is found, the kernel calls the driver's probe() function. The driver parses the properties in the node (memory resources, interrupts, GPIOs, clocks) using Open Firmware (OF) helper functions, configures the hardware, allocates buffers, and exposes the peripheral to user space.

Dynamic Hardware Configuration via Overlays

For SBCs with general-purpose expansion headers (such as Raspberry Pi, BeagleBone, or Orange Pi), hardware can change dynamically depending on the attached add-on board (HAT, Cape, or shield).

Device Tree Overlays (.dtbo) allow small fragments of Device Tree code to be merged into the base Device Tree either during the bootloader stage or at runtime via the kernel's configfs interface. This modifies pin states and activates the necessary peripheral drivers without requiring a complete recompilation of the base system's Device Tree.

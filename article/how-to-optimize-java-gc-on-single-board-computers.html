How to Optimize Java GC on Single Board Computers

Running managed runtimes like Java on Single Board Computers (SBCs) introduces unique performance challenges due to constrained CPU, RAM, and thermal limitations. Default Garbage Collection (GC) settings are typically tuned for multi-core server environments, often causing high CPU utilization and out-of-memory errors on embedded boards like the Raspberry Pi. This guide outlines how developers can optimize garbage collection on SBCs through proper collector selection, explicit memory sizing, JVM tuning, and application-level practices.

1. Select the Appropriate Garbage Collector

Default collectors like G1GC can introduce excessive CPU overhead and memory footprint on low-resource hardware. Matching the collector to the SBC's hardware profile is critical:

  • Serial Collector (-XX:+UseSerialGC): Best for single-core or resource-constrained boards (under 1 GB RAM). It runs single-threaded, avoiding the synchronization and thread-switching overhead of parallel collectors.
  • Parallel Collector (-XX:+UseParallelGC): Ideal for multi-core SBCs where high throughput is prioritized over pause-time consistency, and background thread count can be bounded via -XX:ParallelGCThreads=N.
  • G1 Collector (-XX:+UseG1GC): Suitable only for higher-end SBCs (4 GB+ RAM, quad-core or higher) with strict low-latency requirements.

2. Lock Heap Sizes to Eliminate Resizing Overhead

Dynamic heap expansion and contraction consume precious CPU cycles on low-power chips.

  • Set the initial (-Xms) and maximum (-Xmx) heap allocations to the same value to eliminate runtime heap resizing.
  • Allocate only what the application needs, ensuring at least 25% to 30% of total system RAM remains free for OS operations, I/O caching, and native memory.
java -Xms256m -Xmx256m -XX:+UseSerialGC -jar application.jar

3. Minimize Metadata and Footprint Overhead

The JVM allocates memory for internal structures, class metadata, and thread stacks. You can minimize these auxiliary overheads using specific flags:

  • Reduce Thread Stack Size (-Xss): Lowering default thread stack sizes (e.g., -Xss256k) reduces native memory consumption for multithreaded applications.
  • Control Metaspace (-XX:MaxMetaspaceSize): Set an upper limit on Metaspace to avoid unbounded native memory growth.
  • Disable Unneeded Diagnostics: Disable features like JMX agents and JVM performance counters (-XX:+PerfDisableSharedMem) to eliminate disk and memory overhead.

4. Optimize Memory at the Application Level

Tuning the JVM cannot compensate for inefficient memory usage in code. Implement these design patterns to minimize GC pressure:

  • Avoid Unnecessary Object Allocations: Reuse objects via lightweight pooling for high-frequency tasks instead of creating temporary instances inside tight loops.
  • Use Primitive Types: Prefer primitive arrays over collections of boxed types (e.g., int[] instead of List<Integer>) to avoid object header overhead.
  • Use Off-Heap Memory for Large Buffers: Use ByteBuffer.allocateDirect() for large, long-lived data transfers (such as camera feeds or sensor logs) to keep them out of the GC-managed heap.

5. Consider Alternative Runtimes and Packaging

Standard OpenJDK HotSpot builds may not always be optimal for SBC deployments:

  • Eclipse OpenJ9: Consider using Eclipse OpenJ9 instead of HotSpot. OpenJ9 provides an out-of-the-box smaller memory footprint and uses aggressive memory-saving features like -Xquickstart and -Xtune:virtualized.
  • Modular Runtime with jlink: Build a custom, stripped-down Java runtime image containing only the platform modules your application requires, reducing initial memory overhead before garbage collection even starts.

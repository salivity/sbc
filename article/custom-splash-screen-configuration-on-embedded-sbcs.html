Custom Splash Screen Configuration on Embedded SBCs

Configuring a custom splash screen on an embedded single board computer (SBC) involves displaying branded visuals across multiple boot stages to hide technical console output and reduce perceived boot time. Developers achieve this by configuring visual outputs across three primary phases: the secondary bootloader (such as U-Boot), the Linux kernel initialization, and the early userspace environment. Achieving a seamless, flicker-free transition requires precise framebuffer handling, driver configuration, and kernel argument tuning.

1. Bootloader Splash Screen (U-Boot)

The bootloader is the earliest stage where a display can be initialized. In U-Boot, custom splash screens are implemented through display drivers and environment configurations.

  • Enable Display and Video Drivers: The U-Boot configuration (defconfig) must have display subsystems enabled (e.g., CONFIG_DM_VIDEO, CONFIG_VIDEO_BMP_RLE8, CONFIG_CMD_BMP).
  • Prepare the Image: U-Boot typically requires uncompressed Bitmap (.bmp) images matching the display's exact native resolution and color depth (usually 8-bit, 24-bit, or 32-bit BMP).
  • Store and Load the Graphic: The bitmap can be compiled directly into the U-Boot binary, stored in a raw flash partition, or read from a FAT/ext4 boot partition.
  • Environment Variables: Developers set specific U-Boot variables to load and display the image automatically: 
    setenv splashfile /splash.bmp
setenv splashimage 0x82000000
setenv splashpos m,m
load mmc 0:1 ${splashimage} ${splashfile}
bmp display ${splashimage} ${splashpos}

2. Kernel-Level Boot Logo

During the handoff from the bootloader to the Linux kernel, the display subsystem is re-initialized. Developers can either maintain the existing framebuffer or display a native kernel logo.

  • Custom PPM Replacement: The default Linux Tux logo located at drivers/video/logo/logo_linux_clut224.ppm can be replaced with a custom 224-color ASCII PPM image using tools like Netpbm or ImageMagick: 
    convert -resize 1920x1080! -colors 224 custom_logo.png custom_logo.ppm
pnmnoraw custom_logo.ppm > drivers/video/logo/logo_linux_clut224.ppm
  • Kernel Configuration: Enable CONFIG_LOGO and CONFIG_LOGO_LINUX_CLUT224 via make menuconfig.
  • Suppressing Kernel Console Messages: To prevent boot messages from overwriting the splash screen, modify the kernel command line parameters (bootargs): 
    console=tty1 quiet loglevel=0 vt.global_cursor_default=0

3. Userspace Splash Screen

For complex animations, progress bars, or smooth transitions into the final graphical user interface (Qt, Wayland, or X11), developers employ userspace splash utilities.

  • PSplash: A lightweight, framebuffer-based splash screen utility commonly used in Yocto and OpenEmbedded environments. It accepts input via a UNIX domain socket to draw dynamic progress bars.
    • Generated with gdk-pixbuf-csource into a C header file.
    • Executed as the very first process in the Initramfs or SysVinit/systemd stage.
  • Plymouth: Used on high-resource SBC distributions (such as Debian or Ubuntu-based systems) supporting direct DRM/KMS integration, scriptable animations, and transition effects.
  • Direct Framebuffer/DRM Renderers: Custom scripts using tools like fbi (framebuffer image viewer) or minimal DRM applications launched via early systemd services to draw the final static image before the main application starts.

4. Achieving a Seamless (Flicker-Free) Transition

A common challenge in embedded design is display flickering caused by video hardware being reset between U-Boot, the Linux kernel, and userspace.

  • Simple Framebuffer (simplefb / simple-framebuffer): Configure U-Boot to pass the initialized display buffer memory address to the Linux kernel via the Device Tree (chosen node). This prevents the kernel from resetting the display controller until the native DRM/KMS driver takes over.
  • Continuous Splash Handover: Modern DRM/KMS drivers can inherit the display configuration from firmware without power-cycling display panels or backlights.
  • Tear-Down Synchronization: Ensure that the userspace splash utility does not terminate until the primary user interface is fully rendered and ready to flip the display buffer.

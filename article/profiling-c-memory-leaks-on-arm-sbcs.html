Profiling C++ Memory Leaks on ARM SBCs

Memory leaks in C++ applications running on ARM single-board computers (SBCs) can quickly exhaust limited system RAM, leading to performance degradation or system crashes. This guide outlines the end-to-end process of detecting, isolating, and fixing memory leaks on resource-constrained ARM devices using industry-standard tools like AddressSanitizer (ASan), Valgrind, and Heaptrack.

Step 1: Compile the Application with Debug Symbols

To trace memory allocations back to specific lines of source code, compile your C++ application with debug symbols enabled and omit frame pointer optimizations.

g++ -g -O1 -fno-omit-frame-pointer main.cpp -o my_arm_app
  • -g: Generates debug information (DWARF format).
  • -fno-omit-frame-pointer: Keeps frame pointers intact for accurate stack unwinding on ARM architectures.
  • -O1: Provides basic optimizations while maintaining readable stack traces (avoid -O3 during profiling).

Step 2: Choose the Appropriate Profiling Tool

ARM SBCs have constrained CPU and memory resources. Selecting the right profiling method is essential:

  • AddressSanitizer (ASan): Best for real-time profiling on ARM. Low CPU overhead (~2x slowdown) and moderate memory usage. Requires recompilation.
  • Valgrind (Memcheck): Best for quick diagnostics without recompiling. High CPU overhead (10x–30x slowdown); may run slowly on low-power ARM cores.
  • Heaptrack: Best for visualizing allocations over time and offloading analysis to a desktop PC.

Step 3: Method A – Profiling with AddressSanitizer (Recommended)

AddressSanitizer integrates directly into GCC and Clang, making it the most efficient choice for ARM platforms.

  1. Recompile with ASan flags:

    g++ -g -fsanitize=address -fno-omit-frame-pointer main.cpp -o my_arm_app_asan

  2. Configure ASan environment variables:

    export ASAN_OPTIONS=detect_leaks=1:symbolize=1:abort_on_error=0

  3. Run your application:

    ./my_arm_app_asan

  4. Review the output: Upon application exit, ASan prints detailed stack traces showing the file name and line number where leaked memory was allocated.

Step 4: Method B – Profiling with Valgrind Memcheck

If recompiling the binary is not an option, use Valgrind directly on the target device.

  1. Install Valgrind:

    sudo apt-get update && sudo apt-get install -y valgrind

  2. Execute the binary with Memcheck:

    valgrind --tool=memcheck \
         --leak-check=full \
         --show-leak-kinds=all \
         --track-origins=yes \
         --log-file=leak_report.txt \
         ./my_arm_app

  3. Inspect the generated log: Open leak_report.txt and search for "definitely lost" or "indirectly lost" blocks to pinpoint missing delete or free() calls.

Step 5: Method C – Lightweight Profiling with Heaptrack

Heaptrack records memory events with minimal overhead, allowing you to capture the trace on the ARM board and analyze it visually on a workstation.

  1. Install Heaptrack on the ARM board:

    sudo apt-get install -y heaptrack

  2. Capture the trace:

    heaptrack ./my_arm_app

    This generates a .zst log file (e.g., heaptrack.my_arm_app.1234.zst).

  3. Analyze the report: Transfer the file to your desktop computer and run heaptrack_gui to view allocation graphs, peak memory consumers, and memory leaks.

Step 6: Interpret Results and Apply Fixes

Once the profiling tool identifies the offending code paths:

  1. Locate the allocation point: Match the reported instruction pointer to the file and line number in your source tree.
  2. Implement RAII principles: Replace manual allocations (new/malloc) with smart pointers (std::unique_ptr or std::shared_ptr).
  3. Handle container lifecycles: Ensure dynamic data structures like std::vector or std::map do not grow unbounded during long execution cycles.
  4. Re-profile: Run the application through the profiling tool again to confirm that all leaks have been resolved.
